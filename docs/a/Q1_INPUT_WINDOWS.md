# P1：外部输入集合触发的深度窗口候选

本候选针对有足够独立计算分量、但外部输入并集很大的图。它沿用固定
05f8 的完整分量分核，仅改变 Task 边界，不改变官方局部调度器或配置。
模块为 `src/q1/input_windows.py`。当前不是全量默认求解器。

## 已有证据与假设

044 的 bounded04 四核 E0 为 124268 cycles，新增 DDR 5678624 bytes，
其中 spill 2887424 bytes。静态输入并集为 952928 bytes，大于 L1 的
524288 bytes。大输入集合只是候选触发条件：其全部成员未必同时存活，
内部中间结果、UB、COPY backing、incarnation 与 FIFO 均未由这个数覆盖。
不能将其视为完整峰值、容量非法证据或零 spill 判据。

假设是：按依赖深度切开大外部输入集合，可能减少各个 Task 内先后使用
不同权重引起的重复搬运。代价是新增 Task gates、跨 Task 中间结果搬运、
跨窗口共享输入重载和可能减少流水重叠。质量须用完整 E0 判断。

## 构造与合法性

1. 从 frozen bounded04 获取合法回退与组件核心分配。单核或完整组件不足
   核数时保留原路线。以没有直接计算生产者的张量作为外部输入代理，使用
   图中实际字节数；总量不超过 524288 bytes 时保留原路线。
2. 对官方 COPY 收缩计算 DAG 求最长前驱路径深度。同一深度不含依赖边。
   自浅至深累计这一窗口使用的外部输入并集，新增输入使并集超过
   262144 bytes 时在该深度之前切窗。单层本身超预算则原样保留并如实报告，
   不谎称满足预算。超过 32 个窗口或只有一个窗口，整体回退。
3. 每个窗口中，计算节点保留完整组件原先所属的核，同核归为一个 Task；
   每核按窗口顺序排 Task。映射的原始 op 插入顺序不改。

同一窗口中不同核属于不同弱组件，故无跨核计算依赖；同核在同一 Task。
跨窗口依赖严格增加深度窗口编号，核序也严格增加。完整增广 Task DAG
因此无环。额外调用官方 derive/Task-order 结构验证，但这不证明整个
Step2/Step3 一定成功或更快。最大 32K 个 Task；原 bounded 的1024节点
软上限不在新窗口构造中继续保证，完整大分量仍可能导致编译或内存压力。

拓扑深度处理 O(V+E)，逐层外部输入并集的简单累计最坏 O(D·T)，D 为层数、
T 为外部张量数；装箱 O(V+K·D)，另计既有 bounded、官方图构建/收缩及验证。
没有在线评分、搜索或基于 case ID 的分支。默认字节阈值是启发式工程参数，
不是最优参数，也不满足容量证明的完整条件。

## 冻结的小验证范围

先只测试 **044 / K=4** 的一个候选：默认预算262144、触发524288、最多32窗。
静态预分析预计5窗：深度0–51、52–59、60–66、67–100、101–123；对应输入
并集243424、221184、221184、261120、6016 bytes。这不是正式评分。

新独立批最多1次构造（30秒）+1次外部E0（60秒），总120秒，1worker，
0重试/E1/E2；先固定源码及runner，保留所有成功/失败，复用已发布分母与
bounded044，不重新评价参考值。与主400格同机实验协调资源窗口，不能因
该机制例更好而改动正在运行的固定400格参数或伪造全量组合成绩。

4项图级测试覆盖共享权重在不同深度出现、核分配与前向依赖不变、完整回退、
单层输入超预算不能假称容量安全及参数拒绝。测试使用合成结构，未调用E0。
