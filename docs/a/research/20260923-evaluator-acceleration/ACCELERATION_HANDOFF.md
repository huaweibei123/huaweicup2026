### 1. 不复用答案，也能消除重复工作

`probe/prototype.py` 在独立加载的 E1 私有 runtime 中，维护 Task/算子未完成计数、按官方原序只检查活动 Task、一次分组输出条目；另一组消融再加入 Step3 完成计数、额度 deque 和整数拓扑深度。所有事件、发射/退休时刻、DDR helper、binary64 表达式和 FIFO 顺序保留。

4 核、seed 2026、子图大小 50–100；每引擎预热一次、三次轮换顺序配对，计时从已解析输入到完整结果对象，比较在计时外进行。

| 正式图 | E0 中位秒 | 原 E1 中位秒 | 状态原型中位秒 | 状态原型/E0 配对加速 |
|---|---:|---:|---:|---:|
| 001，1,001 ops | 0.07264 | 0.06636 | 0.05398 | 1.418× |
| 003，13,670 ops | 2.28817 | 1.95369 | 1.32727 | 1.739× |
| 025，23,997 ops | 5.88559 | 4.64199 | 3.72273 | 1.657× |
| 080，1,395 ops | 0.18237 | 0.17345 | 0.11946 | 1.527× |

全部完整对象一致。这四个方案的 spill 新增字节均为零。只改全局状态查询/输出分组的消融已经取得大部分收益；加入其他改动并非每例都更快，025 的该消融反而快于整组。因此让 FAST 分项提交和测量，不机械叠加所有改动。此路线单独未达到通用 3× 门槛。证据：`probe/matrix.json`。

### 2. 最值得交接：固定划分时复用局部编译，全局重新模拟

P1 的局部 Task 编译由原图、划分映射、容量和带宽确定；核分配、核内顺序和核间等待进入后续全局过程。`probe/partition_cache.py` 利用这一边界：

1. 每个候选仍执行官方方案推导及调度合法性校验。
2. 用原图、原始有序 mapping、容量、带宽的完整序列化字节作 key；实例绑定当前代码版本。不同 key 不冒充同一局部行为。
3. 只复用局部构图/Step1/Step2/Step3 成功产物，不缓存全局 Makespan。
4. 命中时为候选独立还原数据，刷新核归属、前驱和 plan view；重新按官方方式建立集合邻接，避免依赖 pickle 恢复 set 的迭代布局。
5. 全局 FIFO、共享 DDR、全部事件、等待及完整输出重新运行。更改等待不需重编译，但必须重模拟。

case_003 固定划分，生成 12 个不同、合法的核分配/顺序候选。每轮从空缓存开始，E0 与原型逐候选交替计时，三轮都逐项比较完整返回对象。

| 轮次 | E0 全批秒 | 原型全批秒 | 全批加速 |
|---|---:|---:|---:|
| 1 | 26.2648 | 6.7686 | 3.880× |
| 2 | 27.3895 | 6.9766 | 3.926× |
| 3 | 26.6146 | 6.9142 | 3.849× |

三轮批加速几何均值 **3.885× E0**。包含首次编译/建立缓存、每次校验、key 序列化、还原、集合重建和完整对象生成；不含解释器启动、图文件读入及结果文件输出。每轮 1 miss、11 hits，复用率 91.7%；缓存 key+value 字节合计 8,897,896（8.49 MiB），额度 16 MiB。候选 Makespan 从 760798 到 774298，确实重新计算了不同全局方案。

**这是明确工作负载上的收益，不是全域 E1 热路径发布成绩，也不是任意搜索都会有 91.7% 命中。** 目前一个图、12 候选，不能替代多图、64 候选池和封存验收。证据：`probe/partition.json`、`reschedule-plans.json`。

### 3. 内存与并发必须实测

`probe/variants.py` 只保留 P1 后续实际使用的局部 Step3 数据；丢弃已完成核查且不再使用的内部历史，官方完整返回字段保留。在 case_003 的 4 个重调度候选、连续两批、单 spawn worker 中，峰值 RSS 从原 E1 的 **299.34 MiB 降至 229.75 MiB，约降 23.2%**。这是进程高水位，不是缓存额度；不证明长时间运行必然保持相同峰值。证据：`probe/memory-large.json`。

64 个不同开发候选（case_001），常驻图，进程间只传计划和紧凑核查结果；每项在 worker 中生成完整返回对象并计算完整结果摘要。并发在途任务最多为 worker 数的两倍。首批包含 spawn/准备，随后两批统计热批平均；表中为热批：

| worker 数 | 原 E1 每批秒 / 次每秒 | 精简原型每批秒 / 次每秒 | 原 E1 / 精简原型 worker RSS 高水位之和 |
|---|---:|---:|---:|
| 1 | 4.296 / 14.90 | 3.552 / 18.02 | 45.09 / 41.63 MiB |
| 2 | 2.403 / 26.64 | 1.766 / 36.25 | 89.89 / 81.36 MiB |
| 4 | 1.229 / 52.08 | 0.953 / 67.14 | 181.27 / 162.98 MiB |

这才是同 worker 预算比较；不能拿四进程新实现除以单进程旧实现，宣称内核快了四倍。RSS 之和并非同刻物理内存峰值，会重复计入共享页，未含父进程（本实验约 32–33 MiB）。4 worker 未测到机器饱和点，不外推 18 核线性扩展。证据：`probe/parallel.json`。

带编译缓存的 case_003 独立测量，12 候选，1/2/4 worker 的热批分别 6.764 / 3.471 / 1.870 秒；worker RSS 高水位之和约 373.64 / 585.22 / 972.36 MiB，父进程另约 41 MiB。**8.49 MiB 的缓存数据绝不等于 8.49 MiB 的评估进程。** 内存不足时应选择更少 worker、无缓存精简路径，或按图/划分分组调度；不能默认所有实验再各自开满 worker。证据：`probe/parallel-partition.json`。

最后的有界回收实验也保留负结果：同 12 候选、单 worker、连续两批，每项结束强制 `gc.collect()` 后，缓存路线峰值仅从 373.64 降至 370.84 MiB，总墙钟 14.04 → 14.21 秒，未见有意义的内存收益，不推荐把强制 GC 当解决方案。在同一有 GC 的协议下，无缓存精简路径约 296.05 MiB / 30.85 秒，缓存路径约 370.84 MiB / 14.21 秒：**缓存用更多内存换来吞吐**。该短实验不构成长跑稳定性证明；不能把前面的 4 候选内存降幅与这里的 12 候选缓存加速拼成一个配置的双重收益。证据：`probe/resources-gc.json`。

后续工程可以分离只读的局部编译数据与每候选可变状态，减少缓存命中时的对象还原/复制；这是针对资源测量提出的待实现方向，尚未以共享对象方式验证，不能直接把原型中的复制全部删除。

### 4. 保留失败路线，避免队友重踩

- 原 64 个随机划分候选中，普通 Step3 缓存 975 miss、0 hit；state 3.371 秒，开缓存 3.540 秒，单次约多 5%。不要在持续改变划分时无条件缓存。
- 固定划分的大图也出现过 16 MiB 缓存循环驱逐：完整局部结果过大，12 候选累计 2,184 miss、0 hit。不是逻辑不可复用，而是缓存粒度与额度不合适。
- 精简后只缓存 Step3 的方案可放入 8.18 MiB，2,002 hit/182 miss；但三轮批耗时约 9.75–10.94 秒，仍慢于复用完整局部编译的约 6.8–7.0 秒。不同消融运行时段有噪声，但收益方向清晰。
- 给当前 E2 输出统一乘常数，哪怕用开发池全部真值选最优系数，P95 最低仍 4.19%，超过 3%。换语言也不改变其模型偏差；见第一阶段报告。

## 正确性与尚未覆盖范围

- 4 个正式图的所有 warmup/配对输出完整一致；64 个原开发池新原型完整输出与已核验 E0 JSON 一致。
- 12 个固定划分新方案，每轮重新调用 E0，比对三轮完整对象；不是只比 Makespan。
- 169 个微输入 × state/lean/Step3-cache/partition-cache 四种原型，共 **676 次严格返回值或异常类型/消息对照，零差异**。沿用独立审查的 900000–900059 生成器家族，在当前原型重新运行。
- **240 次**重复命中、改变核心顺序、改变带宽和等待的额外守卫对照通过；保留输入未被修改的检查。不是完整失效条件证明。
- 现有 E1 的 **11 项** CLI/full/schema 测试在状态+精简原型上通过。编译缓存的正式 CLI/Trace 集成尚未实现；不能把这 11 项算成其全部接口通过。
- 未覆盖 P2/P3 的这种复用、正式大图 spill、长时间内存稳定性、全异常矩阵、跨平台、封存池。P2/P3 的核内编译受完整 COPY/算子顺序影响，严禁直接套用 P1 的 mapping key。

## 后续语言与其他路线

本轮原型仍是 CPython；没有安装或测试新编译工具链。Cython、Rust/C++ 可以作为紧凑数组/热点内核的后续实现候选，先测剩余热点再决定。Cython 的性能依赖恰当静态类型与减少 Python 对象操作；单独释放 GIL 不会让单线程更快，这与本任务大量 dict/set/对象构造有关。[Cython 类型化说明](https://cython.readthedocs.io/en/stable/src/quickstart/cythonize.html)、[GIL 说明](https://cython.readthedocs.io/en/stable/src/userguide/nogil.html)。

当前使用 spawn 多进程符合 Python 3.12 的跨平台启动方式；实测只在本机完成。[Python multiprocessing 官方文档](https://docs.python.org/3.12/library/multiprocessing.html)。E2 仅适合继续作为另行校准的筛选研究；数学等价类复用、P2/P3 增量编译和 GPU 路线尚未在本原型验证，不写进本次收益。

调度提供的 Pro3 外部 S/W 实验与本地机制有相互支持的线索，但环境/方案不同，不能把外部 6.28×、等价池 3.91×混作本机成绩。FORM 对新版原 E1 的 340 条交叉核对也只是成员交接证据，未冒充本原型测试。
