# Q1：真实 Task 剖面驱动的有限拆分/合并

后续对051胜出拆分、044较差合并的定点时间线分析与有限排序对照见 [Q1_TRACE_EXPLANATION.md](Q1_TRACE_EXPLANATION.md)；下列数值保留本轮原始实验身份。

2026-09-24，在 `95bca21` 已有方案上实现下一步实际分区调整。三个公开开发例各比较8个新候选，27次E1调用和6次独立官方CLI全部成功；最终方案的 makespan 与搬运五字段均被E0确认。没有修改冻结官方代码、E1、Q2或队友实现。

## 构造方法与表示边界

`src/q1/profile_candidates.py` 在当前完整计划上调用冻结 `_build_scene_a_tasks`，透明观察真实边界图、Step1完整序列、Step2的初始backing/overflow/spill记录。剖面包括COPY，使用Task本地pos；它不是执行后的物理峰值。候选不继承旧Task的内部执行序列或backing状态。

- 拆分：在真实Step1的首次溢出/最高闭区间压力附近、远端输入消费者之前、远端输出生产者之后提出计算成员前缀切点，并保留中点后备。新Task放在原核相邻位置，获得新ID并重新官方校验、编译。优先级依次偏向实际spill量、首次溢出、远端入口/出口、压力及切点平衡；这是启发式排序，没有用于合法性或收益硬剪枝。
- 合并：只考察同核相邻且在完整“数据依赖＋所有核链”图中满足cover条件的Task，合并后最多256计算算子。按原图张量端点精确计算spill前边界字节节约，再排序。全图生成ID、Step1、spill/backing、全局DDR都交E1重新计算，禁止以节约字节替代真实makespan。
- 每轮至多两个拆分和两个合并，某类不足时由另一类补足。两个回合最多8个新候选；每轮都以该轮开始的同一父计划构造，按E1比较保留更优方案，下一轮才重新剖面。第一轮无改善时第二轮跳过已见输入，继续有限邻域。目标按makespan优先，同分才比较scheduled COPY字节。
- JSON去重和所有计划编辑均保留mapping插入顺序。分区变化后的E1重新编译，不自行做“只失效被改两个Task”的缓存假设。

一般结构合法性仍以官方 `derive_multicore_plan` 和 `validate_task_order` 为准。闭区间压力失败没有被解释为方案非法；有spill的方案仍能胜出。本次没有实现新数学下界，也没有给代理分数冠以最优性保证。

## 预先冻结的预算与失败保全

协议保存在 `results/a/q1-profile-refine-20260924/protocol.json`，在运行前写入。例子与顺序为044、051、002；均用上一轮guided方法的E0确认方案作为输入，固定4核、确定性ID破同分。不是新增封存集，未与随机切点或更强方法做等预算消融。

每例：

- 最多9次E1调用（seed一次＋8个新候选）、2次完整E0 CLI、2次完整Task剖面准备。Task准备包含官方Step1–3，实际成本计入搜索，不能隐去。
- 搜索预算60秒；提议子进程限10秒，E1每次限10秒、worker启动另限5秒。提议前留25秒、评价前留15秒余量；E0的seed与最后确认各限30秒，在搜索预算之外。
- 单独进程组的外层截止125秒，含该例Python启动、读图/计划、全部编译/搜索、E0确认、落盘及清理。三例顺序运行，始终只有1个E1 worker、每worker16 MiB编译缓存。
- 外层约每100ms加`ps`开销采样整个实验进程组RSS，超过1536 MiB即终止该组。包括父进程、提议/E0子进程和E1 worker，共享页重复计数；这是采样停止阈值，允许采样间瞬时超出，不冒称内核硬内存限额，也不是整台机器用量。
- 每次派发前、返回后分别写入并flush/fsync事件账本。提议/评价第一次失败后停止该例；启动或输出异常也留失败记录。缺summary、畸形JSON、账本残行分别标记，不能当作零调用成功。E0确认的seed一直保留，候选只有最后E0确认通过才提升为交付方案。

## 未改善候选与对方向的修正

真实对照表明单指标排序有明显局限，必须把失败候选一起交付：

- **044消除spill反而更慢。** 在Task8的首次overflow附近拆分，spill从76800变为0，但makespan为123363/123168，均差于116227；中点拆分也为122765。增加的边界与Task结构成本没有被“零spill”抵消。
- **044最大边界节约的合并更差。** 合并8与10的预spill边界节约760320，但spill增加到1161472，makespan126094。最终合并6与8只节约471040边界字节，却得到114443，spill74752。观察支持重新编译和精确选优的必要性，不独立识别各因素对时差的贡献。
- **051字节稍增仍更快。** 胜出拆分的scheduled COPY从9570392到9570396，增加4 bytes，makespan减少2641。相反节约65536边界字节的两种合并都较差。没有将其解释为某个等待机制已被独立因果证实；精确时间线分析是后续可做的定点检查。
- **002首轮四候选全部无改善。** 最大节约量的合并达到107573；第二轮保留原父计划、跳过前四输入后，找到88188。此次证明有限扩展候选确有用，不证明当前排序优于随机或任何强基线。

最有价值的下一步是用实际Task时刻与关键等待解释这些动作，改进有限候选排序；当前证据不支持只加大“内存压力”权重，也不支持立刻把所有图/所有切点都枚举一遍。对014大图还没有运行这轮分区调整。
