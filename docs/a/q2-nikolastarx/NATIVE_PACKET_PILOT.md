# P2 在线诊断与关键包候选排序：验证边界

动机来自已归档的两个 069/K5 机制试验：单接收闭包只降低 3 周期；关键下游包按最低计算下界选出的方案却增加 500 周期。后者不能证明整个候选族无用，但已经不足以支持继续用该下界作工期预测。

`critical_packet_exchange.propose` 返回由当前关键通信连接产生的至多 16 份去重完整方案。种子由当前 trace 的正暴露延迟选择，至多 8 条；每条只有同核关键后继的唯一闭包和两种固定拓扑交织。没有随机排列、用例编号分支、参数网格或历史成绩回填。计算/FIFO 下界仅用于排除不可能严格改善 incumbent Makespan 的方案，其余候选直接评分。这是有明确结构与停止边界的局部改进，仍不保证全局最优或每例有效。

`native_trace_diagnostic.diagnose` 在调用方独占的 E2 worker 内短暂包装已有 `_build_scene_b_tasks`，捕获**同一次 native 请求**的完整 prepared 图，再恢复原函数。不会另做一次 prepare。核对 prepared 原操作身份、类型、Pipe 与计划的核归属，完整 debug start/end 和全部发射门槛一致后，才输出当前关键原操作和跨核连接。该关键图固定了这次实际 COPY 时长，不是改动后的节省证书。

## 第一份兼容与机制试验

`scripts/q2_packet_native_pilot.py` 固定一份旧 069/K5 输入；先用在线 E2 完整逐操作时刻、工期、流量与既有 E0/contract 配对。旧证据只用于独立核对，候选构造仅使用新在线诊断。随后调用一次 propose，并依固定顺序评每份不同完整候选，严格按 (Makespan, added DDR bytes) 选优。有严格改善才再启动一次未修改官方 E0，复核最佳候选。

预算为 1 worker、总远端活动 120 秒、512 MiB 监控上限、native E2 至多 17 次（1 次基线诊断 + 至多 16 候选）、独立 E0 至多 1 次、单独 prepare/E1/fallback/重试为 0。E2 和 E0 自身的准备计在各自调用与总墙钟里；候选数上限不是耗时保证。异常或未知调用结果即停止并归档。独立 VM lease/watchdog 另限制整个云端生命周期。

本试验复用已有 SHA 固定的 Linux native 二进制；在新的运行环境核查源码、ELF、ABI、ctypes 字段偏移并记录 Python、NumPy、系统身份。旧 build receipt 仅证明二进制来源，不能伪装成新环境已验证；不修改生产求解器原有 runtime 守卫。逐时刻配对与最佳方案 E0 复核才是这次实际兼容证据。

此前只有合成测试通过；本文件不声明真实 E2 集成或新成绩完成。即使单例获得改善，也还需要从原始图在线生成 incumbent 的冻结统一求解器及全 100×5 实验，不能把已存计划或单格最优拼成正式 benchmark。
