## 标量 DP 为什么不够

DP 正确优化的是恰四个连通块的最大标量计算总量，其证明与 576 个新增小树 oracle 见 `THEORY_REVIEW.md`。它没有把 pipe 重叠、跨块生产先后、COPY/MTE 队列和内存补边的等待放入目标。

- 002 的四块为 `[53892,88284,45468,88284]`。较轻的 core0 最后完成；其 M 在 42268～85057 间空闲 42789 cycles，两个较重核心在 84428 已结束。相同最大块重量下的不同切点、块归属与局部顺序可能给出不同尾部，C 无法区分。
- 063 的四块为 `[244332,353244,177948,353244]`。core0 的 M 在 167836～336265 间空闲 168429 cycles，最终反而拖到 400563。块重量较小不保证更早完成。
- 062 的最大标量块为 890136，实际整图却只需 847213；M/V 可重叠工作，所以不能把标量 C 当成官方下界，也不能计算“距 C 尚差多少”来宣称接近最优。

063 的 tensor `1000010624` 从 core3 输入 core0：源 COPY_OUT 在 335636 结束，固定 500 延迟后于 336136 释放，但目标 COPY_IN 到 379429 才开始，post-release 等待 43293。其 MTE2 前一个操作 `1000013896` 在 344113～344190 执行，随后又空闲 35239 cycles。因此“仅因前一个 COPY 占槽”不足以解释全部等待。保存结果没有展开该目标的完整内存/前驱边列表，本文不从空闲长度单独断言某条具体补边的因果，也没有运行反事实评估。002 对应晚到 COPY 的 post-release 等待仅 747，062 三条连接均在释放时立即发射。

这批数据表明只压低跨核字节或最大标量重量仍有改进空间。下一步应构造能够显式处理生产释放、pipe 工作向量或共享输入消费顺序的规则，再独立冻结小批证伪；不能直接把三图事后赢家做成隐含的 case 路由。
