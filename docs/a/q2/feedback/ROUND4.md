## 原件支持的机制观察

**002：允许更多块后计算负载更均匀。** R4 的 397 个 packet 在四核的标量计算工作为 `[69576,68820,68640,68892]`，而 R3 四个连通块为 `[53892,88284,45468,88284]`。R4 四核 M 忙时恰好均为 60000，内部空闲为 `[4140,980,112,1922]`；R3 为 `[47001,6912,3600,6912]`。R4 最终 67136，比 R3 94419 降低 28.90%。与此同时跨核 tensor pair 从 3 增到 190；这些事实与更细分核和流水改善负载相符，但这次同时改变切分和顺序，不能把收益单独归因于某一个环节。

**016/024：均匀计算负载仍留下通信等待。** 016 有 7015 packets、3963 个跨核 pair，四核 V 忙时约 191.8～193.8 万，内部空闲仍约 62.6～64.5 万 cycles。024 有 2323 packets、1311 个跨核 pair。固定跨核延迟、COPY/队列释放仍会影响完成时间；当前时钟模型没有因此成为精确调度器。016 比已有较强方案退步的 10000 cycles 需要后续针对依赖与队列的证据，不能仅用平均负载解释。

**064：模型与真实时序间仍有明显差距。** 652 packets、190 个跨核 pair；估计 pipe horizon 为 15395，理想计算坐标为 9517，实际为 18216。四核标量负载 `[5884,5336,9183,2649]` 不均，M 内部空闲各约 1.38～1.57 万；模型没有给出接近官方极限的证据，也不宜据此声称只需调整某个常数即可追回 1601 cycles。

**共享组：效果不等于容量保证。** 028 将 153 个同签名分量分组，067/073 走全局共同输入的阶段顺序，均无跨核 tensor pair，但 028/067 仍有 spill。058 保持 255 个完整分量为 packet，窗口为每核 3，仍有 23633920 spill bytes。有限 packet 窗口限制的是构造器活跃块数，不能充当 L1/UB 驻留上界。

完整逐核四 pipe 的计算负载、最终忙时、内部/前后空闲、最大三段内部间隔、COPY 数量与跨核释放等待均在 `round4/measurement-audit.json`。MTE 忙时已含 DDR 竞争，跨核等待可能重叠，不可将所有等待相加当作 Makespan；最大单次等待也不等于关键路径损失。保存结果没有展开所有内存依赖边，本报告没有仅凭一个空闲间隔断言具体补边因果。

后续方法应继续围绕实际暴露的问题提出可证伪结构规则：控制细分造成的通信等待、改善对短异构图的分核、在共享输入分层时约束张量生存期。保持一份冻结可执行方法，扩展实测范围；不按这些 case ID 事后固定赢家，也不将三条路由的开发均值外推全库。
