# 全文语言规范与共同审阅方式

标准版本：2026-09-27.1。要求来自本轮用户明确反馈；语言条目的具体通过条件以同一提交 `catalogue.json` 中 L01—L13 为准，图内与图注分工另见 V03；全部为阻断项。适用范围包括标题、摘要、正文、图内文字、图注、表注、算法说明和附录。

## 先把事情讲清楚

不能用几个概括词替代读者理解所需的内容。“三种硬件语义”没有告诉读者赛题 A、B、C 三种情况分别规定了什么。作者须先按题面说明执行方式、带宽、存储容量、缓存使用等具体规则及差异，再说明算法如何处理这些规则。参数必须核原题，不凭印象补写。摘要可以简洁，但仍要保留理解方法所需的关键内容。

“统一框架”“分层建模”“结构依据”“评价闭环”同样不能代替实际说明。要说清输入是什么、生成的方案包含什么、怎样生成和检查、用什么评价、依据哪个指标保留结果。概括性名称只有在前文解释充分、后文可以唯一回指时才有意义；增加英文或换一个概括词不算改好。

## 术语和关系必须准确完整

- 禁止自造黑话与含混简写。先核权威资料里的完整英文词或短语、准确含义，再优先选官方中文译名。无官方译名时用清楚准确的中文并标明来源；中文技术术语后紧跟精确英文。不要为普通汉语机械添加英文，也不要自造英文替中文黑话辩护。
- 按用户对检查点02的最新批注，正文通常写“核心”，图中可用Core；首次出现时先定义NPU及其计算核心，附准确英文原词，并解释图中Core的对应关系。这替代此前正文Core必须保留英文的约定。Task、Cache、Pipe、DDR、COPY_IN、COPY_OUT、ID和符号仍须按题面与本文对象准确说明，不能仅列英文省略定义。
- 首次使用前说明对象、动作、条件、范围与单位。通用词典定义不能替代本文语境；临时约定要明示并给例子。不能首次解释后再次省略关键关系。
- “流水”不能用 pipeline 是标准词来辩护。确指流水线时写全“流水线（pipeline）”并解释本文阶段及关系；实际指不同执行单元在时间上重叠执行时，直接说清相应操作、单元和条件。
- “同核子图”应展开为“被分配到同一个核心的各个子图”。若将它们合并为一个Task，再说明这个执行任务与各子图的关系。先解释整张计算图、子图和对应计算任务；描述执行动作时写“子图对应的计算任务”等准确对象，不把图本身当作执行对象。

## 每句和每段都要符合中文论文表达习惯

图件也按逐句标准审核。流程图节点和连线只写识别对象、动作与分支所需的短标签；较长的定义、适用条件、例外、评价次数、结果解释和局限，应完整且准确地写进图注或紧邻正文。移出图内文字不是删去科学内容，图注也不能靠黑话或压缩句式承担解释。图内标签、图注与正文在论文实际插入尺寸一起审阅：读者应能找到每个符号的定义，并能不靠猜测理解每条分支。对应验收项为 V03。

逐句检查主体、动作、对象、并列成分、指代和适用条件；拆开连续名词和过长定语，按中文顺序表达。术语已经有定义，也不能使一个拗口或无法理解的句子自动合格。

逐段检查定义与解释的先后、论题是否明确、推理是否连续。先正面说明方法，再在相关位置说明限制；不要堆方法标签、自我评价或反复否定。因果和比较必须有前提、同条件数据或推导依据；指标、单位、比较对象和样本范围要明确。可并行执行不等于实际已测得加速。

`sentence-audit.json` 的 SP-002 和 SP-022 是具体示范。它们不是全部问题清单。没有关键词命中也必须逐句回读；不能用修改少数词代替整段重写。

用户每次指出的实例通常代表一整类问题。应从实例归纳共同缺陷，全文检查含义相同但用词不同的位置，回报实际修改范围与剩余问题；不能只改被圈的一处或只搜索原词。提出方法和证明前，应先交代问题、风险与为何需要该方法，例如先解释循环等待如何产生，再说明无环条件和证明。

## 人工批注补充的全文要求

- 小标题直接说明本节研究对象和内容，去除“先按……”等草稿计划口吻，以及“三个决策”“一份方案”等缺少指代的概括。
- 首次建立重要统一约定时，按用户要求对完整约定克制地加粗，避免只突出碎片或大量加粗；须在新PDF中检查。
- 按用户对本篇论文的要求，明确由研究者进行论证，例如“通过反例，我们说明……”。这是本篇写作要求，不能外推为所有中文论文的语法定律。
- 依赖关系首次出现时，交代两端操作、谁产生及读取什么数据、由此形成的先后要求；按实际方法区分直接关系、经路径传递的关系和共享输入。
- 删除混入成稿的作者内部规范、自我提醒、写作计划和自我辩护。应实际解释六种情形，无须再告诉读者“不把六种情形写成六个无需解释的机制名称”。评价上限、跳过条件、证明假设和结论范围仍须保留，改为准确、面向读者的条件陈述。
- 数学量、上下界和代价都须明确对象、单位、固定条件和适用方案集合；公式相加各项须具有可相加的量和单位，不能把操作次数复杂度直接与秒相加。

这批要求来自CP02的USER-CP02-07至17。USER15/16为同句跨行两次选择，保留两个事件、合并一个问题位置；不重复计数，也不按用户估计的数量凑出问题。已完成的一般初审不冒充上述新增类别的全文专项复核。

## 一份记录，多方接收

共享通道为组织主库 Issue 217。验收台、Fang 图件工作台、实际改图会话和整稿会话都引用同一份固定标准及问题记录。原图件任务继续保留，各方通过评论链接关联，不复制出互相矛盾的规则。每次实质交付前补查标准变化。

双向主动同步、人工批注回传、实际已读回执与冻结稿件的具体步骤，按同目录 [COLLABORATION_PROTOCOL.md](COLLABORATION_PROTOCOL.md) 执行。

每条问题记录必须包含：标准版本、被审源稿完整 SHA、稳定问题 ID、文件和行号或确定的 PDF 页码、逐字原句或原段、具体问题、要求怎样修改、建议改文及其适用条件、所缺定义或来源。无法确定科学含义时明确交作者解释，审阅者不得猜造。

作者回应逐条引用 ID，交改文位置和固定新 SHA；被删除、合并、拆分的原句仍保留映射。语言改写涉及算法含义、假设、公式或数据时单独指出。旧稿标注不得静默套在新稿行号上。

发出、本人已读、作者已修改、验收者已回读分别记录。各会话亲自回报实际已读的标准提交、理解例子与影响范围；一次账号级“收到”不能代表所有会话执行。共享 Issue 不提供实时唤醒保证，未回执者保留待签收。

## 子 Agent 的分工和限制

按完整章节或段落分工，给必要的前置定义和相邻语境，不把句子完全孤立。较轻模型适合初审、位置整理和覆盖检查；语义模糊、中文论证和科学含义由主验收者复核。已完成的初审使用 Sol / medium，不声称启用了未提供的 Luna。用户最新分工下，验收台只维护网站、接口与记录，不主动派新标注；后续检查和整改由原写作任务监督Antigravity组织并交回。

已完成的一般初审每名软预算 12000 tokens、最多 30 次工具调用、12 分钟；评价器调用为零。实际 token 不可见时记不可用。只在各自独立报告文件写标注，不修改作者稿件，不复制全队历史，不递归拆分。

每个输入单元记录“发现问题”“本轮未发现问题”或“缺上下文”。这些是审阅覆盖信息，不是最终验收通过。主验收者核对原句与来源，复核问题及建议后再交作者；新 PDF、图内文字、术语权威来源与数学结论仍需各自核验，不能被文字初审代替。
