# 问题一：子图独立执行场景下的多核切分与调度

## 硬件执行语义与多核调度的权衡机制

在问题一的系统设定中，每个非空子图 $s \in \mathcal{S}$ 均被底层编译系统独立封装为一个物理硬件任务（Task）。由于子图之间在硬件执行层面上严格隔离，芯片私有缓存无法实现跨 Task 的数据保留。无论两个具有数据依赖关系的 Task 最终被指派至同一个计算核心还是不同的计算核心，它们之间传递的中间数据张量均必须通过外部主存（DDR）进行持久化中转，即由前驱 Task 将生成张量执行 `COPY_OUT` 写出至 DDR，再由后继 Task 执行 `COPY_IN` 从 DDR 读回片上缓存。

设 Task $s$ 在指派核心 $a(s)$ 上的开始执行时刻与完成时刻分别为 $A_s$ 和 $F_s$（单位为 cycle）。记 $\mathrm{prev}(s)$ 为排定在同一核心上紧邻 $s$ 之前执行的 Task，$\operatorname{pred}(s)$ 为在数据依赖关系上先于 $s$ 执行的全部前驱 Task 集合。底层离散事件评测系统对硬件调度时序施加了如下物理约束：

$$A_s \ge F_{\mathrm{prev}(s)} + \Delta_{\mathrm{local}}, \quad \Delta_{\mathrm{local}} = 100 \text{ cycles},$$

$$A_s \ge F_t + \Delta_{\mathrm{sync}}, \quad \forall t \in \operatorname{pred}(s) \text{ 且 } a(t) \ne a(s), \quad \Delta_{\mathrm{sync}} = 1000 \text{ cycles}.$$

其中，$\Delta_{\mathrm{local}} = 100$ cycles 为同一核心上相邻任务间的上下文切换开销；$\Delta_{\mathrm{sync}} = 1000$ cycles 为跨核心依赖同步屏障引入的硬件等待时延。若某项约束中的前驱对象不存在，则对应不等式不生效。

上述时序约束揭示了多核心切分与调度决策中的基本权衡关系（trade-off）：

1. **并行收益与排队削减**：将互无计算依赖的算子划分至不同的子图并分配给多个计算核心，能够让无依赖的算子在物理分离的流水线（`PIPE_M` 与 `PIPE_V`）上并发推进。虽然这并不改变由原始数据依赖所决定的固有关键路径长度，但能够显著缩短由于单核执行资源有限而被强制串行化的排队等待时间；
2. **通信开销与同步代价**：若子图切分引入了跨子图的数据流动边界，中间数据张量必须通过 DDR 进行读写传递，从而产生额外的数据搬运开销与总线争用；当数据依赖跨越不同核心时，更会触发长达 1000 cycles 的跨核同步屏障等待。此外，若多个核心并发访问 DDR，还可能引发内存总线带宽争用，增加各 Task 的实际等待时间。

因此，多核心切分并非越细越好。只有当并发执行所节省的排队等待周期足以弥补切分所引入的 DDR 搬运与跨核同步开销时，切分方案才能实现全局执行时间的净收益。

## 结构化候选方案生成与多级细化策略

基于上述物理权衡，算法首先分析输入计算图的数据流动特征。若仅考虑算子之间的直接与间接计算依赖，能够沿无向连通边相互到达的算子子集构成了一个弱连通分量（weakly connected component）。不同连通分量之间天然不存在计算依赖，但在读取共享外部输入时仍可能产生总线访问争用。

针对该计算图结构，算法参考前序研发建立的分叉阶段与前沿子树划分策略，在统一求解入口（`unified.py`）中设计了六类互补的基础结构候选生成器。针对给定用例与核心数 $K$，求解器至多构造六种不同侧重点的基础方案：

1. **连通分量前沿划分与大任务重组（`bounded`）**：首先调用树状前沿划分模块（`tree_frontier.py`，参数 `packet_factor=4`）生成初始划分；随后对操作数超过 4096 的巨型任务进行内部扫描，在不切断任何依赖链的前提下识别其内部独立的计算连通分量，按目标约 1024 个算子的粒度安全重组为独立子图，作为基础参考方案；
2. **大工作量后缀波次剥离（`heavy-or-sink`）**：当单个主要分量在主导流水线上的计算量占比达到或超过 80% 且分量数充足时，将该瓶颈分量的末端汇点算子剥离为粗粒度后缀波次（若不满足触发条件则回退至分层剥离汇点算子的 `sink_peel` 候选）；
3. **过载连通分量切分（`overload`）**：针对单个连通分量在任一流水线上的计算工作量超过全系统平均核心公摊配额的情形，将其剥离出的独立算子包按负载均衡启发式分配至轻载核心，摊薄瓶颈核心的计算压力；
4. **共享输入开销感知划分（`shared-input`）**：当连通分量数不小于核心数且外部输入张量总大小超过 $524{,}288 \text{ B} = 512 \text{ KiB}$ 时，统计各分量对外部输入数据的共享重叠度，将重度共享同一张量的分量优先归并至同一核心，以抑制重复 DDR 搬运总量；
5. **前沿子树划分与并行展开（`fork-frontier`）**：采用前序研发建立的分叉阶段与前沿子树划分策略，并推广至无分叉链及内向树（in-trees）结构，沿拓扑阶段以前沿粒度（`grain=4`）将不相交的子树打包分配至各核心，挖掘拓扑天然存在的横向并行性；
6. **受限链状结构私有化（`capacity-return`）**：严格识别私有的矩阵-向量链-矩阵模式（$M \to V^+ \to M$ 且矩阵算子数恰为分量数 2 倍），在片上缓存容量满足保守估算的前提下进行局部紧凑分组，规避中间向量张量的外存溢出。

在上述基础方案的基础上，求解器通过两级进阶细化模块展开多级候选探索：

- **动态分组长度细化与拓扑保形顺序（`structural_refine.py`）**：在基础候选选优结果的基础上，一方面对链状流水结构进行分组长度调整（至多产生 1 次在线评测）；另一方面尝试 `paced` 与 `root-heavy-fused` 两种拓扑保形执行次序（至多产生 2 次在线评测；输入错峰候选的单例时间线见附录D图\ref{fig:p1-paced-diagnostic}），从中优选出性能最佳的父级方案 $P_{\mathrm{parent}}$；
- **分支援助重分配（`branch_aid.py` & `branch_refine.py`）**：针对父级方案中各核心在同一拓扑阶段负载失衡的情形，通过桥树分析识别可转移的独立计算分支，将其重分配至同波次已有任务的轻载援助核心（至多产生 1 次在线评测）。

全流程严格采用精确模拟器 E1 进行在线评分与方案筛选，且每一阶段均执行完整的字节级哈希去重与格式合法性校验。未产生新结构或与已有方案完全重复的候选不参与评测，全流程在线 E1 评测调用次数严格限制在 10 次以内。

```python
# 输入：原始计算图 graph，核心数 cores (1..5)
# 输出：合法的多核心切分与调度方案 plan
# 1. 求解父方案：基础候选(<=6次) + 动态分组(<=1次) + 保形顺序(<=2次)
parent_plan, parent = structural_refine.solve(graph, cores)
if not (2 <= cores <= 5) or not valid_parent_evidence(parent, parent_plan):
    return parent_plan  # 单核或父方案证据无效时安全返回父方案
parent_obj = objective_pair(parent.get("selected_objective"))

# 2. 构造分支援助候选并执行结构校验（异常捕获回退父方案）
try:
    candidate, diag = branch_aid.construct(graph, cores, parent_plan)
    if diag.get("status") != "candidate-unscored":
        return parent_plan  # 结构不支持或软耗时超限安全回退
    if plan_bytes(candidate) == plan_bytes(parent_plan):
        return parent_plan  # 方案字节完全重复，跳过评测
    validate_candidate(graph, cores, candidate)
except Exception:
    return parent_plan      # 构造或校验异常安全回退父方案

# 3. 至多发起 1 次在线 E1 评测（全流程评测总预算 6 + 1 + 2 + 1 <= 10 次）
try:
    score = score_once(graph, candidate)
    if score.get("status") == "ok":
        cand_obj = objective_pair(response_refine.objective(score))
        if cand_obj < parent_obj:
            return candidate  # 按严格字典序改善时采纳新方案
except Exception:
    pass
return parent_plan
```

## 分支援助重分配机制与无环性形式化证明

为了在不打破原有稳定调度结构的前提下进一步压低瓶颈核心的执行延迟，本文设计了分支援助重分配机制（Branch-Aid）。该机制以 `structural_refine` 输出的优秀方案作为父级解 $P_{\mathrm{parent}} = (\pi_0, a_0, \sigma_0)$，仅在多核心场景（$2 \le K \le 5$）下尝试对同阶段核心负载进行横向均衡。

![典型用例 case_026（5 Cores）独立分支重分配前后的切分结构映射。展示原始划分中 Core 0 上的超大任务解构为保留在 Core 0 上的独立支路 Y（算子 710、712、720）与汇合计算 J（算子 724、726），以及重分配至 Core 1 的导出独立支路 X（算子 714、716、722）。图中黑实线表示计算依赖，橙虚线表示跨子图数据依赖，点线端口表示连接至局部裁剪窗口外部的算子依赖（非孤立无依赖节点）。图示仅对应特定用例局部的 8 节点子图结构，不代表构造器处理的一般计算图全局结构。](../figures/fig-p1-cuts-xy-corrected.png){#fig:p1-cuts width=100%}

::: algorithm {#alg:p1-branch-aid title="分支援助重分配的波次分支选择与分配算法"}
```python
# 输入：核心数 cores、波次 h 与各核任务 by_core，预处理 view_nodes, ops, pred, succ, direct_succ，当前任务数 n_tasks 与起始 ID next_id，既有累积拆分 pieces
# 输出：该波次更新后的拆分记录 pieces 与援助核心分配 placement
members = {c: set(view_nodes[t]) for c, t in by_core.items()}
packets = {c: _packets(g, pred, succ) for c, g in members.items()}
# 假定算子包单汇点合法且同高任务间无跨核计算边（外围已做结构守卫与异常抛出）
loads = {c: compute_pipe_work(g, ops) for c, g in members.items()}
for c in range(cores):
    loads.setdefault(c, Counter())  # 其余未分配任务的核心补空计数器
total = sum_loads(loads.values())   # 汇总全核流水线工作量
if not total:
    return pieces, {}
pstar = min(total, key=lambda p: (-total[p], p))  # 确定主导流水线 p*

# 角色互斥划分：捐赠核心高于平均工作量，援助核心低于平均且已有任务
donors = [c for c in by_core if cores * loads[c][pstar] > total[pstar]]
helpers = [c for c in by_core if cores * loads[c][pstar] < total[pstar]]
if not donors or not helpers:
    return pieces, {}

# 经桥树分析识别可导出的独立支路 X、保留支路 Y 与汇聚 J
found = []
for c in sorted(donors):
    if (w := witness(by_core[c], members[c], packets[c], pred, succ, direct_succ, ops)):
        w["core"] = c
        found.append(w)
if not found:
    return pieces, {}
found.sort(key=lambda w: (-max(w["work"].values()), w["export_pred"]))  # 工作量大、前驱小优先

# 贪心指派 X 至增加后负载最小的援助核心（单个 helper 可接收多个 X）
new_loads = {c: Counter(loads[c]) for c in range(cores)}
placement = defaultdict(list)
for w in found:
    new_loads[w["core"]].subtract(w["work"])  # donor 扣除 X 工作量
    def key(c):
        after = new_loads[c] + w["work"]
        return max(after.values(), default=0), sum(after.values()), c
    helper = min(helpers, key=key)
    new_loads[helper].update(w["work"])       # helper 增加 X 工作量
    placement[helper].append(w)
    w["helper"] = helper

# 检查最大流水线负载严格下降，且受构造器任务容量上限限制
old_max = max(max(loads[c].values(), default=0) for c in range(cores))
new_max = max(max(new_loads[c].values(), default=0) for c in range(cores))
if new_max >= old_max or n_tasks + 2 * (len(pieces) + len(found)) > max(320, n_tasks):
    return pieces, {}

# 记录 X/Y/J 映射：X 导出至 helper，Y 与 J 保留在原 donor
for order, w in enumerate(found):
    pieces[w["task"]] = {"X": next_id + 1, "Y": w["task"], "J": next_id,
                         "helper": w["helper"], "wave": h, "export_order": order}
    next_id += 2
return pieces, placement
```

### 拓扑波次与援助角色判定

算法将父方案中的全部 `COPY` 节点暂时收缩，构建关于 Task 顶点的有向依赖图 $G_{\mathrm{task}} = (\mathcal{S}_0, E_{\mathcal{S}_0})$。对于每个 Task $s \in \mathcal{S}_0$，定义其拓扑高度（height）为从任意源点 Task 出发到达 $s$ 的最长依赖路径边数：

$$h(s) = \begin{cases} 0, & \text{若 } \operatorname{pred}(s) = \emptyset, \\ 1 + \max_{t \in \operatorname{pred}(s)} h(t), & \text{若 } \operatorname{pred}(s) \ne \emptyset. \end{cases}$$

算法要求父方案必须严格满足**波次单调推进性质**：在每一个核心 $k$ 的执行序列 $\sigma_{0,k}$ 中，Task 的执行次序必须沿高度 $h$ 严格单调递增，即若 Task $s$ 排定在 Task $t$ 之前，则必有 $h(s) < h(t)$。因此，在任意固定高度 $h$ 处，每个核心至多分配有一个 Task。将高度为 $h$ 的全部 Task 构成的集合记为波次 $W_h$。

算法遍历每个波次 $W_h$，并检查以下强约束条件：

1. **同波次无依赖条件**：在波次 $W_h$ 内部，来自不同核心的 Task 之间不得存在任何直接或间接的计算算子数据依赖，即不同核心在该阶段处理的计算任务在拓扑上完全独立；
2. **流水线负载统计与角色划分**：统计波次 $W_h$ 内各核心在各个实际出现的执行流水线上的有效计算工作量 $\operatorname{work}(c)[p] = \sum_{v \in T_{h, c}, \operatorname{pipe}(v) = p} \max(1, \operatorname{cycles}_v)$，确定该波次全系统工作量最大的主导流水线 $p^*$。在主导流水线 $p^*$ 上，满足 $K \times \operatorname{work}(c)[p^*] > \operatorname{total}[p^*]$（即本核工作量严格高于全波次平均工作量）的核心被判定为**捐赠核心候选（donor candidates）**；满足 $K \times \operatorname{work}(c)[p^*] < \operatorname{total}[p^*]$ 且在波次 $W_h$ 处分配有原有独立任务 $T_{\mathrm{orig}}$ 的核心被判定为**援助核心候选（helper candidates）**。捐赠核心集与援助核心集基于主导流水线负载严格角色互斥，在该波次完全空闲（未分配任务）的核心不进入援助核心集合；
3. **桥树（Bridge-Tree）分解与算子三相划分**：在捐赠核心的原始任务 $T_{\mathrm{donor}}$ 内部，通过 Tarjan 算法寻找无向图中的桥边，并将桥边割开后的各个双边连通块压缩为节点，构建**桥树（bridge tree）**（而非基于割点的块割树）。若存在唯一的内部汇点算子，且存在一个汇聚算子 $j \in T_{\mathrm{donor}}$ 恰好接收两条来自独立前驱的桥边输入，则将 $T_{\mathrm{donor}}$ 严格划分为三个互不相交的算子子集：
   - **导出独立支路 $X$**：由其中一条前驱支路及其全部上游算子构成的独立连通块，被选定为迁移至援助核心的子图；
   - **保留独立支路 $Y$**：由另一条前驱支路、其余上游算子以及该 Task 内可能存在的其他独立连通分量构成，继续保留在原捐赠核心上执行；
   - **汇合计算部分 $J$**：由汇聚算子 $j$ 及其在 $T_{\mathrm{donor}}$ 内部的全部后继后代算子构成，继续保留在原捐赠核心上执行。

### 依赖关系与全序构建规则

三相划分在算子依赖结构上严格满足：

- $X \cap Y = \emptyset$，$X \cap J = \emptyset$，$Y \cap J = \emptyset$，且 $X \cup Y \cup J = T_{\mathrm{donor}}$；
- $X$ 与 $Y$ 之间不存在任何正向或反向的数据依赖边；
- 所有跨子集依赖边均由 $X$ 指向 $J$ 或由 $Y$ 指向 $J$；$J$ 绝不存在指向 $X$ 或 $Y$ 的反向反馈边；
- $X$ 与 $Y$ 的所有外部前驱算子均来自高度严格小于 $h$ 的前驱波次任务。

在调度序列重构中，算法支持一个援助核心在同一波次批量接收来自不同捐赠核心的多个独立导出支路 $X_1, X_2, \dots, X_m$：

- **捐赠核心的执行时序**：原 Task $T_{\mathrm{donor}}$ 所在位置被替换为子图 $Y$ 与子图 $J$ 的顺次执行，即在捐赠核心上 $Y$ 紧邻排定在 $J$ 之前（$Y \to J$）；
- **援助核心的执行时序**：援助核心在执行其原有波次任务 $T_{\mathrm{orig}}$ 之前，优先顺次排定执行其接收到的全部导出支路 $X_1, X_2, \dots, X_m$，即援助核心上的执行序列构型为 $X_1 \to X_2 \to \cdots \to X_m \to T_{\mathrm{orig}}$；
- **核心内波次推进时序**：在每个核心的本地调度序列中，任务严格按高度递增排列，不同高度的任务顺序受本地排队序列与跨核数据依赖约束，并非在全芯片施加全局物理同步屏障。

### 扩展依赖图无环性证明

**命题4.1（分支援助重分配的无环性）。** 在上述波次推进、同波次独立性、三相依赖分解以及调度构建规则下，重分配后的新方案 $P_{\mathrm{new}}$ 所诱导的扩展依赖图 $D^+(P_{\mathrm{new}}) = (\mathcal{S}, E_{\mathcal{S}} \cup E_\sigma)$ 必然不存在有向环。

**证明。** 根据命题 3.1，只需构造一个严格单调的整数标号函数 $r: \mathcal{S} \to \mathbb{Z}$，使得图中的每一条有向边 $(u, v) \in E_{\mathcal{S}} \cup E_\sigma$ 均满足 $r(u) < r(v)$。

对于任意子图 $s \in \mathcal{S}$，设其在原始依赖图中所归属的波次高度为 $h(s)$。为每个波次 $h$ 分配基准标号区间 $[100h, 100h + 99]$。在波次 $h$ 内部，针对不同角色子图定义整数标号如下：

1. 对于任意援助核心 $c \in H_h$，设其接收到的导出支路序列为 $X_1, X_2, \dots, X_m$。由于每个捐赠核心至多导出一个分支 $X$ 且捐赠核心与援助核心互斥，必有 $m \le |D_h| \le K - 1 \le 4 < 10$。其原有的波次任务记为 $T_{\mathrm{orig}}$。定义：
   $$r(X_i) = 100h + 10 + i, \quad \forall i \in \{1, 2, \dots, m\},$$
   $$r(T_{\mathrm{orig}}) = 100h + 30;$$
2. 对于任意捐赠核心 $c \in D_h$，其分裂出的子图为 $Y$ 与 $J$。定义：
   $$r(Y) = 100h + 10, \quad r(J) = 100h + 40;$$
3. 对于既非援助核心亦非捐赠核心的正常核心上的原有任务 $T_{\mathrm{norm}}$，定义：
   $$r(T_{\mathrm{norm}}) = 100h + 20.$$

现在逐一验证扩展依赖图 $D^+(P_{\mathrm{new}})$ 中的所有可能边 $(u, v)$：

- **情形一：跨波次边**。
  - 对于数据依赖边 $(u, v) \in E_{\mathcal{S}}$：若 $u$ 与 $v$ 属于不同波次，由于 Task 拓扑高度的定义，所有外部前驱的高度严格小于后继任务的高度，故必有 $h(u) \le h(v) - 1$。因此 $r(u) \le 100h(u) + 50 \le 100(h(v) - 1) + 50 = 100h(v) - 50 < 100h(v) + 10 \le r(v)$，整数标号严格递增；
  - 对于同一核心上的调度次序边 $(u, v) \in E_\sigma$：由于新方案严格保持波次单调推进，不同波次间的调度边同样满足 $h(u) < h(v)$，故必然有 $r(u) < r(v)$。
- **情形二：同波次内的核心调度边 $(u, v) \in E_\sigma$**。
  - 在援助核心上，调度序列为 $X_1 \to X_2 \to \cdots \to X_m \to T_{\mathrm{orig}}$。根据标号赋值，显然有 $r(X_1) < r(X_2) < \cdots < r(X_m) < r(T_{\mathrm{orig}}) = 100h + 30$；
  - 在捐赠核心上，调度序列为 $Y \to J$。根据定义，$r(Y) = 100h + 10 < r(J) = 100h + 40$；
  - 其余核心在波次 $h$ 内至多只有一个任务，不存在同波次调度边。
- **情形三：同波次内的数据依赖边 $(u, v) \in E_{\mathcal{S}}$**。
  - 根据同波次无依赖假设，波次 $h$ 内不同原始任务之间不存在任何计算依赖边；
  - 唯一可能存在同波次数据依赖边的仅为由原任务分裂出的子图对。根据三相划分的依赖性质：
    - 若边为 $X_i \to J$，则 $r(X_i) \le 100h + 20 < 100h + 40 = r(J)$；
    - 若边为 $Y \to J$，则 $r(Y) = 100h + 10 < 100h + 40 = r(J)$；
    - $X_i$ 与 $Y$ 之间无依赖边；$J$ 绝无指向 $X_i$ 或 $Y$ 的依赖边；
    - 导出支路 $X_i$ 与援助核心原有任务 $T_{\mathrm{orig}}$ 原本分属不同的独立任务，二者之间不存在任何数据依赖边。

综上所述，扩展依赖图 $D^+(P_{\mathrm{new}})$ 中的任意有向边 $(u, v) \in E_{\mathcal{S}} \cup E_\sigma$ 均恒成立 $r(u) < r(v)$。根据命题 3.1，图中绝不存在有向环，调度方案在拓扑执行时序上是严格死锁自由的。 $\square$

需要特别指出的是，命题 4.1 所证明的无环性构成了调度方案物理可执行的必要条件，但拓扑无环并不自动等价于片上存储资源不发生溢出。新增的子图切分改变了数据常驻生命周期，可能引发片上缓存动态容量紧张。因此，生成的候选方案必须在后续阶段由精确离散事件模拟器进行完整的容量验证与执行评分。

## 工程保护机制与终止条件

为确保算法在复杂计算图上的执行可控性并避免不必要的评测开销，求解流程配备了严谨的资源保护与防退化机制：

- **任务数量工程规模约束（`TASK_LIMIT = 320`）**：若父方案的任务总数已达到 320，直接跳过分支重分配；若新方案任务数超过 320，同样予以拒绝。该上限用于控制离散事件评测与后继编译的规模；
- **结构检查软时间预算（`EXTRA_SECONDS = 2.0s`）**：在桥树分解与波次图遍历等深层图算法中设置 2.0 秒的软预算检测点。若遍历耗时超过该阈值，算法定期退出分析并安全抛出 `UnsupportedStructure` 异常回退至父级方案，避免在极端复杂图上陷入长时遍历；该软检测点不构成求解器端到端总耗时的硬性上限，外部离散评测耗时仍需另行累计；
- **单次评估预算受限**：分支重分配阶段至多允许发起 1 次额外的 E1 在线评测。全流程累计 E1 调用次数严格受限于 10 次；
- **严格字典序选优准则**：新方案以 $(M_1(P), \text{scheduled\_copy\_bytes})$ 为内部评价目标向量，仅在其严格呈字典序优于父方案时方予采纳。由于对于同一输入计算图，方案的调度复制总量与额外 DDR 搬运量之间满足恒等式 $\text{scheduled\_copy\_bytes} = \text{original\_copy\_bytes} + \text{extra\_ddr\_bytes}$（其中原始输入输出搬运字节数 $\text{original\_copy\_bytes}$ 恒为确定常数），在固定输入图下该规则等价于本队按 $(M_1(P), \text{extra\_ddr\_bytes})$ 字典序择优的次序；此字典序平局规则为本队内部多候选比较选择策略，而非官方对多指标评价的硬性等价规定。

## 典型案例微架构执行时序分析（Case 026）

为了在微架构时钟周期与硬件流水线级别理解分支援助细化的执行特征，我们选取典型用例 `case_026`（5 Cores 配置）进行结构与时序分析。

该用例在分支援助重分配前后的宏观指标对比体现如下：

- **细化前父方案**：由 `structural_refine` 生成 5 个 Task。官方 E0 仿真评测的 Makespan 为 44,114 cycles，调度产生的额外 DDR 搬运量为 211,680 字节；
- **细化后采纳方案**：经 `branch_aid` 调整后扩展为 7 个 Task。官方 E0 仿真评测的 Makespan 缩短为 42,014 cycles，调度产生的额外 DDR 搬运量为 375,532 字节。

方案调整使得该用例的全局完成时间降低了 2,100 cycles（完成时间降幅为 4.76%），其代价是额外 DDR 数据搬运量增加了 163,852 字节。
