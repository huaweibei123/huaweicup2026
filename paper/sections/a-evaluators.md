# 双层评估器的首轮设计与开发证据

为降低候选切分方案的筛选成本，我们将评估过程分为等效候选 E1 与快速代理 E2 两层。最终成绩始终由冻结的官方评估器 E0 复算；本节结果是首轮开发证据，尚未经过独立封存验收。

## E1：索引化 Task 边界构图

E1 保留官方 Problem 1 的 Step1--3、全局合法性检查、事件模拟及结果组装，只改写 Task 边界构图。原实现会在多个 Task 上重复扫描 tensor 及其生产者、消费者；改写后先建立 Task--tensor 触及关系、有效生产/消费关系和 Task 内直接边，再逐 Task 访问相关对象。官方完整 CLI 的原始 profile 显示，在 case 003 上总耗时 49.463 s，其中 `evaluate_scene_a` 和 `_build_scene_a_tasks` 分别累计 33.901 s 和 19.720 s，边界扫描相关生成式累计 5.326 s；因此选择该处作为首个局部热点。profile 同时显示 JSON 序列化累计 14.790 s，说明函数内加速并不能直接代表完整 CLI 加速。

在 Windows 11、Python 3.12.13、4 核方案、固定 seed 2026 的三例开发矩阵中，我们对 E0 与 E1 的完整函数返回对象作严格递归比较，不使用浮点容差；每例预热 1 次并配对重复 5 次。结果如下。

| 图 | E0 中位时间 / s | E1 中位时间 / s | 配对加速几何平均 | full 差分 |
| --- | ---: | ---: | ---: | ---: |
| case 001 | 0.6594 | 0.5577 | 1.0910 | 0 |
| case 019 | 0.4968 | 0.4450 | 1.1193 | 0 |
| case 080 | 1.4722 | 1.2911 | 1.1642 | 0 |

case 001 有 4/5 个正式配对不低于 E0 的 0.8 倍，case 019 和 080 均为 5/5；三例 1.09--1.16 倍的配对几何平均仍明显低于 3 倍研发门槛。因此 E1 目前只能视为有限范围内的零差分候选和局部热点增量，不能称为已通过高速验收。Problem 1 CLI 已在一个成功样本上验证结果 JSON、Trace 和日志逐字节等同官方，并在一个非法 plan 上验证相同退出码、stdout/stderr 和不落结果；现有证据仍未覆盖 Problem 2/3、100 个正式图或完整失败矩阵。

## E2：静态负载与通信排序代理

E2 v0 在同图常驻上下文中对候选方案做结构校验，然后以三部分构造排序分数：每核 Pipe 累计负载上界、粗粒度 Task 依赖上界和 Task 边界搬运代价。记二者前两项为 $B_{\mathrm{pipe}}$、$B_{\mathrm{dep}}$，边界搬运量为 $D_{\mathrm{boundary}}$，带宽为 $b$，则

\[
s(P)=\max\{B_{\mathrm{pipe}}(P),B_{\mathrm{dep}}(P)\}
     +D_{\mathrm{boundary}}(P)/b.
\]

$s(P)$ 是同图同配置下的无量纲排序分数，不是 cycles。代理不执行 Step2 spill、Step3 Pipe FIFO 与内存复用边，也不模拟共享 DDR 争用；因此它将执行检查标为 `unchecked`，并输出 `spill_unmodeled`、`step3_order_ignored`、`ddr_contention_aggregated` 等风险标签。Problem 2/3 明确不支持。

首个开发池取 case 001、Problem 1、4 核，共 64 个候选，短名单保留 8 个；所有候选均有 E0 真值。该池中短名单遗憾为 0，保留了距 E0 最优值 1% 内的候选，同池 Spearman 为 0.8568。内存内常驻直调时，E2 累计 0.3560 s，E0 full 累计 28.7685 s，观察比为 80.82 倍。该比较不含图准备、gzip/文件输出、E1 精筛与 E0 最终确认，也不是 E2 对 E1 的同池配对速度。为保留可复核真值，64 份 E0 full 结果以确定性 gzip 保存，并同时记录压缩与未压缩字节 hash。

更重要的是，rank-only 路线没有输出校准 Makespan，因而无法计算要求的相对误差中位数和 P95；上述单图开发池也没有与校准集、封存集分离。所以 `quality_gate_passed=false`，80.82 倍和零遗憾均不能解释为“高速低误差”发布验收通过。

## E2 第二路线与原生探索

第二条算法路线不使用全局聚合分数，而是在每个 Task 内对各 Pipe 做确定性 list schedule，把每次 Task 边界 COPY 单独取整，再沿 Task 依赖及同核顺序传播完成事件。它在 FORM 提供的开发反例上表达了同核/跨核固定等待差异：两个搬运统计相同的方案，官方与该模型均得到 1052 和 152 cycles。不过，在同一 64 候选开发池上，该路线的 Makespan 相对误差中位数为 25.76%，P95 为 28.90%，最大值为 30.70%，64 个候选全部超过 3%。其短名单遗憾仍为 0、Spearman 为 0.8127，但数值门槛明确失败。

作为语言实现探索，我们还将一个隔离的固定点排序小内核分别写成 Python、C++17 和 Rust。MSVC 19.35 实际编译的 C++ 对 512 个候选产生了与 Python 完全相同的 31,387 字节输出，SHA-256 为 `30b2a06e...e25f3186`；保存实验中的进程级中位数为 39.49 ms 与 256.87 ms。Rust 因本机没有 `rustc`/`cargo` 而未运行。该结果仅说明合成小内核的跨语言字节一致性和工程成本，不使用官方 I/O，也不构成 E2 误差或端到端速度证据。

## 适用范围与后续验证

当前混合流程仍是研究设计：E2 负责粗筛，E1 负责高可信精筛，E0 负责最终确认。正式结论需要在同一提交和同一封存范围内同时验证 E1 零差分与至少 3 倍、E2 相对合格 E1 至少 10 倍、校准 Makespan 误差中位数不超过 1%且 P95 不超过 3%，并报告多池短名单损失和完整链路成本。第二种 E2 算法与 C++ 小内核已有真实失败/工程证据，但 Rust、Problem 2/3、合格 E1 对照及独立封存验收均尚未完成。
