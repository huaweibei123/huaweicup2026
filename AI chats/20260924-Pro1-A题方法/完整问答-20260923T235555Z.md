## 一、先校正研究对象：你们不是在自由设计一个 NPU 调度器

这一点决定后面几乎所有工作是否值得做。

你们实际提交的是两个对象：每个非 COPY 操作属于哪个子图，以及每个核心执行哪些子图、按什么顺序执行。**Task 内部的拓扑排序、缓存换入换出、多 Pipe 排布，由官方程序完成。**最终 Makespan 又由共享带宽的多核模拟器统一计算，不能拿自己设计的理想调度时间替代。:chatgpt-content-reference{index="0"} :chatgpt-content-reference{index="1"}

因此，前面“先建立可信 evaluator”的方法论，在这份题上要落实为：

**封存并读透官方 evaluator，增加独立合法性检查、微型测试与诊断工具，而不是另写一套评分规则。**

### 三个问题，不能只改一个“通信系数”

题面第 5 页图 3 展示的区别非常关键：场景 A 的同核子图之间也需要 DDR 中转；场景 B 才允许同核子图保留核内数据。问题 2、3 进一步明确，同一核心的所有子图合并为一个 Task。:chatgpt-content-reference{index="2"} :chatgpt-content-reference{index="3"}

| 问题 | 实际通信与同步规则 | 我会优先研究的决策 |
|---|---|---|
| 问题 1：场景 A | 每个子图一个 Task；跨子图都经 DDR；同核前一 Task 完成后等待 100 cycles，跨核前驱 Task 完成后等待 1000 cycles | **子图粒度**：何处值得切开，何处必须融合 |
| 问题 2：场景 B | 每核一个合并 Task；同核可复用；跨核 COPY_IN 等待源 COPY_OUT 完成及 500 cycles 同步延迟 | **数据归属与生命周期**：哪些操作放在同核、如何安排消费顺序 |
| 问题 3：场景 B 加 L2 | 沿用问题 2，增加共享只读 FIFO Cache；命中不刷新 FIFO 顺序 | **共享输入的到达时序**：如何让复用真正发生，而不是仅在图上“存在共享” |

这些同步规则的准确含义见附录 D，尤其问题 2、3 等待的是对应数据的 COPY_OUT，而不是等待源核心整个 Task 全部完成。把它们错误地建模成“整个核心任务完成后另一个核心才能启动”，会丢掉题目允许的并行空间。:chatgpt-content-reference{index="4"} :chatgpt-content-reference{index="5"}

另外，题目明确希望避免暴力迭代搜索，单个用例以 5～10 分钟内得到结果为佳。**四机资源可以支持研发阶段的大量对照实验，但最终提交的算法不能靠长时间穷搜成立。**:chatgpt-content-reference{index="6"}

## 二、统一建模：外层优化方案，内层接受官方“编译与执行”

我会把切图、分核、排序分别记为 P、a、π，把场景记为 σ。主问题写为：

\[
(P^\star,a^\star,\pi^\star)
\in
\underset{(P,a,\pi)\in\mathcal F(G,N,\sigma)}
{\arg\min}
\;
T_{\mathrm{official}}(G,P,a,\pi;N,\sigma).
\tag{1}
\]

这里，可行域包含节点覆盖、子图依赖无环、调度顺序合法，以及经过官方展开后能够满足存储与执行约束。

**额外搬运量和 Cache 命中率保留为辅助指标，不自行发明一个综合分数替代 Makespan。**题目将 Makespan 列为最重要指标，另外两项为次要指标。:chatgpt-content-reference{index="7"}

式（1）不是让我们直接把官方程序当黑箱乱搜，而是强调：**所有近似模型的作用都是指导决策，最终效果必须回到官方执行语义。**

### 第一层抽象：用“通信域”统一三问

定义一个操作所在的数据复用域：

\[
d_\sigma(o)=
\begin{cases}
P(o), & \sigma=\text{场景 A},\\[2mm]
a(P(o)), & \sigma=\text{场景 B 或场景 B 加 L2}.
\end{cases}
\tag{2}
\]

它表达了一个简单但重要的区别：

在问题 1 中，跨子图就跨越了核内复用边界；在问题 2、3 中，同核的不同子图仍可能属于同一个复用域。

于是，三问可以共享一套张量分析、结构识别和优化框架，而不是分别写三套互不相干的算法。

### 第二层抽象：通信对象应当是张量，而不只是操作之间的边

假设一份输入被十个操作共同使用。

把这些操作分到几个 Task、每个 Task 如何读取，比“总共切断了多少条操作依赖边”更接近实际通信代价。题面本身也强调，共享输入被分散到多个子图或核心，会产生重复读取。:chatgpt-content-reference{index="8"}

因此，我建议内部同时维护两种图：

**操作依赖 DAG**负责拓扑、关键路径和合法性；**以张量连接生产者与消费者的有向超图**负责复用与通信分析。

这不是为了给普通图算法换一个高级名字。有向无环超图划分已有对应研究，研究对象就包含数据流、多生产者或消费者关系，以及划分后商图仍无环的约束，可以直接借鉴其建模与粗化方法。:chatgpt-content-reference{index="9"}

但文献中的通信目标不能直接当作本题评分函数。**同一张量的边界写回、目标 Task 读取如何去重，必须再用官方源码核实。**

## 三、最值得押注的三个研究假设

这三条是我认为最有希望形成“数模之星级研究主线”的地方。不是说它们已经被证明有效，而是它们分别对准了题目的真实机制，并且都能设计明确的反证实验。

### 假设一：真正决定切分质量的是“张量复用收益与并行损失”，不是普通割边权重

对于一组强关联操作，合并可能减少边界搬运、重复读取和 Task 开销，但也可能减少并行度、延长数据驻留、增加换入换出。

题目甚至明确提醒：子图过大时，固定启发式核内调度器可能产生大量换入换出，合并后的执行时间可能反而更差。:chatgpt-content-reference{index="10"}

因此，主算法不应该采用“通信越强越合并”的单一规则，而应该考虑：

**这次合并减少了什么搬运，释放或占用了什么并行资源，又让哪些张量活得更久。**

我会做一个最小实验：选取一类共享输入明显的子结构，逐步增加融合规模，测量 Makespan、边界搬运、缓存换入换出、Cube/Vector 利用情况。

值得寻找的不是一条永远下降的曲线，而是：

> **融合规模增大后，先因减少通信而变好，再因并行度或缓存压力而变差。这个转折能否由可观测特征预测？**

若能预测转折，算法就获得了“自适应选择子图粒度”的依据，而不只是调出一个固定子图大小。

### 假设二：问题 2 的关键不只是“分到同核”，而是“让数据在合适的时间被消费”

场景 B 中，数据可以留在核内，但驻留不是免费的：它持续占用 L1 或 UB，可能挤走其他数据。官方缓存策略又基于固定序列和下一次使用位置决定换出对象。:chatgpt-content-reference{index="11"} :chatgpt-content-reference{index="12"}

因此，两个方案即使有相同的核心分配，也可能因为子图组织与顺序不同，产生不同的核内顺序和换入换出。

**这里有一个很值得深挖的控制手段：通过可提交的子图划分和顺序，影响固定调度器的行为。**题面明确说，问题 2、3 的合并 Task 会在不破坏依赖的前提下，按照 `core_schedules` 调整子图间顺序。:chatgpt-content-reference{index="13"}

具体可以探索“生产—集中消费—尽早释放”的顺序设计，而不是只让两个通信量大的操作同核。

这与红蓝卵石游戏所研究的“有限快速存储与数据搬运之间的权衡”存在直接联系。但本题的换入换出规则是固定的，不能把允许自由调度、自由重算的理论模型直接搬过来。理论应帮助我们识别生命周期和通信下界，而不是改变题目允许的动作。:chatgpt-content-reference{index="14"}

对应的关键实验是：

**固定核心分配，只改变子图组织和合法顺序。**

这样才能分清性能提升究竟来自分核，还是来自对官方核内调度器的有效引导。

### 假设三：问题 3 中，“同时读取同一输入”可能反而破坏预期的 L2 收益

这一条尤其值得尽早验证。

题面规定：COPY_IN **发射时**查询 Cache；未命中则读 DDR，**完成后**才插入 Cache。命中不改变 FIFO 顺序。:chatgpt-content-reference{index="15"}

由此可以提出一个待检验的推论：

**多个核心在第一次读取完成之前同时请求同一张量，可能都发生 miss，而不是自动共享一次 DDR 读取。**是否存在同张量在途请求合并，需要查源码，不能自行假定。

如果这个现象成立，就可以研究“先完成一次填充，再安排其他相关读取”的合法顺序设计。但这里有两个限制：

第一，输出接口没有“任意插入等待”“新增预取操作”之类的控制项，必须通过允许的子图安排影响发射顺序。第二，不同 Pipe 可以并行，不能认为在前面放一段计算，就一定推迟后面的读取；必须用 Trace 确认实际效果。:chatgpt-content-reference{index="16"} :chatgpt-content-reference{index="17"}

我会把它设计成一个对照实验：

**同一组共享输入、同一核心分配，比较最大并行启动与复用感知排序。**同时改变共享工作集和复用间隔，观察收益是否因 FIFO 淘汰消失。

这一方向的价值在于，它研究的是**调度与 Cache 的相互作用**，而不只是“加了 Cache 所以更快”。

## 四、主算法：多层次构造，瓶颈驱动修正，少量官方评估

我不建议最终交付“遗传算法、粒子群、模拟退火各跑一遍取最好”的大拼盘。

我会采用下面这条主流程：

> **结构分析 → 多种有物理依据的初始方案 → 无环约束下联合切分与分核 → 存储与顺序优化 → 少量官方评估 → 针对瓶颈修正。**

### 1. 先生成“图的结构画像”

第一轮拿到正式数据后，要统计的不只是节点数，而是：

操作关键路径、可并行分支、Cube/Vector 工作量分布、共享输入消费者集合、张量大小分布，以及若干合法顺序下的活跃张量规模。

同时检查有没有重复计算块、长链、分叉—汇合结构、窄接口连接的大块区域。

**现在还不能断言正式数据属于哪一种结构。**真正的算法资源分配应由这些统计决定，而不是凭题目名称想象数据分布。

### 2. 保留少量机制不同的初始方案

我会至少实现三类候选：偏关键路径与并行度、偏张量复用与低通信、偏缓存安全与短生命周期。

关键路径优先、最早完成时间选择，可以参考 HEFT 一类列表调度思想，作为基础构造方法；但本题有多 Pipe、固定核内展开和动态共享带宽，必须重新设计成本估计。:chatgpt-content-reference{index="18"}

每一类候选都要是真正不同的结构选择，而不是同一算法换十个随机种子。

### 3. 粗化不能破坏无环性

这里有一个非常容易出错的地方：

**原图是 DAG，不意味着任意分组后的子图依赖图还是 DAG。**

例如，一个三节点链，把第一个和第三个放到同一子图，中间节点放到另一个子图，就会得到两个子图相互依赖。题目明确禁止这种划分。:chatgpt-content-reference{index="19"}

因此，初版可以采用较保守的合法构造：从全局拓扑序的连续片段开始；后续再加入更灵活的无环合并和边界移动。

**尤其不能在问题 2 中简单把“核心编号”当作“子图编号”。**同一核心可以承接多个分散的子图；这些子图在评估阶段合为 Task，不等于提交阶段可以随意合成一个可能产生环的子图。

### 4. 分核要考虑资源向量，不只看总 cycles

一个核心上的 Cube 和 Vector 可以并行，四条 Pipe 则各自串行。用所有操作 cycles 的总和代表核心负载，会忽略这种结构。:chatgpt-content-reference{index="20"}

所以，给子图安排核心时，至少同时估计矩阵计算负载、向量计算负载、搬入搬出需求、依赖到达时间和核内存储压力。

我们真正想获得的是：

**不同资源的工作相互重叠，强复用数据尽量留在合适的位置，关键操作不要被无关工作拖延。**

不要求机械地把所有核心“填满”。输出允许某些核心的子图列表为空；是否多用一个核心，要看其并行收益能否覆盖新增搬运和同步成本。:chatgpt-content-reference{index="21"}

### 5. 局部修正必须对应可解释的瓶颈

我会优先实现几种明确的修改：合并高代价边界、拆开导致严重换入换出的区域、移动一组共享输入的消费者、交换合法的子图顺序，以及重排影响关键数据到达的工作。

不要无差别随机修改整张图。

特别要避免一种错误直觉：**DDR 搬运越并行，性能就一定越差，因此应该全部错峰。**官方模拟器是共享总带宽，并发变化会重新分配带宽。减少并发本身不会凭空减少总搬运工作量；只有改善关键计算的启动、计算通信重叠或 Cache 命中，才可能缩短 Makespan。:chatgpt-content-reference{index="22"}

### 6. 官方评估次数由时间预算决定

候选先经过静态成本、局部生命周期分析等便宜检查，只把少量有希望的方案交给官方 evaluator。

先测一次完整评估需要多长时间，再决定每个实例可以承担多少次校准。**如果一次官方评估已经很慢，最终求解器就必须更多依赖开发阶段学到的构造规则，而不是把大量评估塞进线上求解过程。**

这里要严格区分：

**研发时可以四机并行发现好规则；提交时，所有内部评估和搜索都必须计入实际求解成本。**

## 五、理论深度：重点做下界、结构特例和可证伪机制

你前面强调的“寻找数学结构，而不只是现学一堆算法”，在这道题上是有落点的。

但我不会把时间主要花在写一个覆盖所有细节、最终求不动的巨大整数规划上。

### 一个应尽早建立的基础下界

设纯计算关键路径长度为 Lcomp，全部矩阵操作与向量操作的周期总量分别为 WM、WV，必须经过 DDR 的数据量下界为 Dmin。在相应必需流量假设核实后，可以建立：

\[
T^\star
\ge
LB
=
\max\left\{
L_{\mathrm{comp}},
\frac{W_M}{N},
\frac{W_V}{N},
\frac{D_{\min}}{B_{\mathrm{DDR}}}
\right\}.
\tag{3}
\]

理由分别是：依赖链无法并行消除，全部矩阵或向量工作分别受到核心数量限制，必需 DDR 流量受到总带宽限制。本题 DDR 总带宽固定为 60 bytes/cycle。:chatgpt-content-reference{index="23"}

这里要非常谨慎：**不能把当前方案实际发生的全部搬运量，直接当作所有方案都必须付出的通信下界。**当前方案的重复读取和换入换出，恰恰可能是可优化的。

对于一个已验证的可行解，下界可以给出：

\[
0
\le
\frac{T_{\mathrm{alg}}-T^\star}{T^\star}
\le
\frac{T_{\mathrm{alg}}}{LB}-1.
\tag{4}
\]

右侧是相对最优性差距的上界，不是“测出了真实最优差距”。下界很松时，它也可能没有多少判别力。

### 精确方法主要放在两个位置

**极小图的完整验证。**对足够小的图枚举合法切图、分核和顺序，调用官方评估器；只有确实覆盖完整可行空间，才称其为该小图的最优解。

**识别出来的结构特例。**例如窄接口连接的重复块，可能适合动态规划或局部精确重排。能否成立取决于结构与状态规模，不预先承诺。

这里必须避免一个常见问题：用 CP-SAT 求解一个忽略共享带宽、固定 COPY 耗时的简化模型，然后把结果称为本题的全局最优。**那只能是简化模型的最优。**

我希望理论线最终至少回答一个实际问题：

> 什么结构下应优先融合，什么结构下应优先并行，什么结构下性能已经接近资源下界？

这比单纯证明一个宽泛的复杂性结论，更能支撑你们的算法。

## 七、实验设计必须能支撑“为什么有效”，不只是“结果更好”

### 先建立强而公平的基线

至少要有关键路径列表调度、通信感知的融合调度，以及一个考虑存储或资源负载的加强版基线。

题目提供的随机生成脚本明确只是接口演示，不是性能基线。**战胜它不能证明算法有竞争力。**:chatgpt-content-reference{index="25"}

所有算法在同一配置、同一运行预算下比较。不能自己的方法选四台机器跑一晚上的最好值，基线只运行一次。

### 三组关键消融

我会围绕前面的假设设计：去掉张量共享信息，只用普通边代价；去掉生命周期和换入换出感知；去掉问题 3 的复用时序设计。

但每次消融都要重新生成对应方案，保持比较预算一致，而不是只在论文里把某个系数设为零，其他流程仍隐含使用被移除的信息。

### 问题 3 做一个交叉对照

分别得到“无 L2 优化方案”和“考虑 L2 的优化方案”，再交叉评估：

| 调度方案 | 无 L2 | 有 L2 |
|---|---|---|
| 无 L2 优化得到的方案 | 基准结果 | 固定方案下的硬件收益 |
| 考虑 L2 优化得到的方案 | 检查是否只是一般调度改善 | 硬件与新调度共同作用的结果 |

这样能够区分“硬件变强了”和“算法确实利用了新硬件”。

这不意味着所有格子都会更好；**有解释力的失败结果也应保留。**

### 统计口径必须从第一天统一

题目要求的平均加速比，是先计算每个用例的加速比，再进行算术平均：

\[
\overline S_\sigma(N)
=
\frac{1}{M}
\sum_{i=1}^{M}
\frac{T^{\mathrm{fixed\ single}}_i}
{T_{i,\sigma,N}}.
\tag{5}
\]

不能用“全部单核时间之和除以全部多核时间之和”替代。单核基准也必须采用题目规定的固定启发式结果；题目明确允许因基准启发式非最优而出现超过核数的加速比。:chatgpt-content-reference{index="26"}

因此，超过核数的加速比不能自动当作错误，也不能被包装成突破并行计算理论限制的发现。

### 固定硬件，改变工作负载，研究适用区间

官方算法评估必须使用规定配置，不得通过改配置制造更好结果。:chatgpt-content-reference{index="27"}

补充机制实验可以在固定硬件下，改变合成图的共享工作集、计算与搬运比例、分支宽度、张量大小和复用间隔。这样能观察算法在何处由计算受限转为带宽受限，或由复用收益转为缓存压力。

最终我希望看到的，不只是平均加速比，还有**逐用例表现、求解时间、退化案例，以及少量能解释机制的执行时间线**。官方已经输出可供 Perfetto 查看、分析的 Trace，可以直接利用，不必先做一个新的可视化平台。:chatgpt-content-reference{index="28"}

|---|---|---|
| 前 15% | 官方语义、数据画像、统一接口、强基线 | 三问都有可运行、可评估的完整路径 |
| 15%～40% | 主线、挑战线、理论线并行探测 | 每条路线至少有一个支持或反驳假设的实验 |

```text
        ▼
第二轮：各分支再次使用自己的原始 16 KiB 输入
经过 ADD、RELU、RELU、REDUCE
        │
        ▼
再次归约，接少量末端操作
```

例如，第一条分支的原始输入张量 `117` 供操作 `154` 使用，经若干操作到 `160` 完成第一轮归约；同一个输入张量又被第二轮操作 `291` 使用，而 `291` 还要等待广播张量 `290`。这是文件里的真实依赖，不是为解释算法构造的例子。:chatgpt-content-reference{index="4"} :chatgpt-content-reference{index="5"}

两轮的每条主要分支都有 4 个计算操作，每个 268 cycles，因此每条分支的计算工作量为 **1,072 cycles**。中间许多标量操作只有 **13 cycles**。

这个结构把三问之间的区别变得非常具体。

### 问题 1：主要矛盾是并行收益与 Task 同步开销

应该优先在**大数据已经归约成小结果的位置**考虑划分，而不是在一条连续的 16 KiB 数据处理链中间随意切开。

但是，**2 字节边界并不等于便宜边界**。问题 1 的跨核前驱 Task 等待是 1,000 cycles，与一条主要分支的全部计算工作量已经处于同一量级。同步约束取相应前驱完成时间和等待时间的最大值，不能把全图每条边的等待简单累加。:chatgpt-content-reference{index="6"}

因此，我会首先比较两种结构化方案：

**按阶段分批。**把若干第一轮分支合为一个 Task，分配给不同核心；归约区域另行组织；第二轮也按批次安排。目的是保留并行度，同时减少碎片化 Task 和不必要的等待层次。

**归约节点与相关分支联合分组。**把原图中已有的部分归约节点放入合适的 Task，减少跨 Task 的依赖层次。这里仅改变分组和分配，**不重新结合运算、不改写归约树、不改变原图计算**。

这比“按固定节点数切图”更贴近真实代价。

### 问题 2：主要机会是跨阶段保持输入的数据归属

对同一条分支，第一轮和第二轮都需要同一份 16 KiB 原始输入。

场景 B 允许同一核心的多个子图共用一个 Task，保留核内数据；跨核才插入边界搬运和同步等待。:chatgpt-content-reference{index="7"}

所以一个值得优先验证的方案是：

> **第一轮与第二轮的对应分支尽量放在同一核心，但仍然表示为不同阶段的子图；在中间归约和广播期间保留原始输入。**

五核下，每核承接两三份这样的输入，单看这些输入的驻留体积并不大。是否能够与该核其他工作共存，要再结合完整生命周期及官方排布判断。

这里还藏着一个很容易犯的错误：

**“前后两段放在同核”不等于“前后两段合成同一个子图”。**

如果把第一轮分支和它对应的第二轮分支合成一个子图，却把中间归约放在外面，就会出现：该子图先向外部归约提供数据，随后又依赖外部归约返回结果。这样会形成子图依赖环，而题目明确禁止这种划分。:chatgpt-content-reference{index="8"}

所以这一题很适合你强调的结构化思考：**数据归属、子图划分、执行阶段，必须是三个不同的概念。**

### 还要同时考虑 Cube 与 Vector 的搭配

这个样例既有上述大块纯 Vector 工作，也有明显偏 Cube 的其他部分。

我会把“将不同资源需求的工作安排到同核，以争取 Pipe 重叠”纳入候选构造，而不是只按总 cycles 均衡。题面也明确指出，同核 Cube 与 Vector 可以独立并行。:chatgpt-content-reference{index="9"}

## 二、源码核对后，有几项规则必须重新写进团队的共同模型

题目要求输出的是子图归属和每核子图顺序，内部展开与最终 Makespan 由提供的评估程序决定。因此，我们优化的不是一台可以任意重排指令的理想 NPU，而是**这个固定展开与执行流程下的方案空间**。:chatgpt-content-reference{index="0"} :chatgpt-content-reference{index="1"}

### 1. 最终执行遵循固定 Pipe FIFO，不会自动跳过受阻操作

源码中的流程是：

先生成扩展序列，再把它投影到各条 Pipe，形成固定的操作顺序；多核阶段只能发射当前 Pipe 的队首操作。

这意味着：

**一个 Pipe 的队首还在等待跨核数据时，后面即使存在数据已经就绪的独立操作，也不一定能越过去执行。**

因此，普通的“负载均衡＋通信最小化”模型可能给出一个看起来很好的分配，实际却让各核频繁等待。

更准确的研究对象，是问题 2、3 展开后的执行图：

\[
H(P,a,\pi)
=
\bigl(
V_{\mathrm{expanded}},
E_{\mathrm{data}}
\cup E_{\mathrm{memory}}
\cup E_{\mathrm{FIFO}}
\cup E_{\mathrm{cross}}
\bigr),
\qquad
H(P,a,\pi)\ \text{必须无环}.
\tag{8}
\]

其中，切分、分核和顺序共同决定展开后的操作、内存复用边、Pipe 顺序边和跨核依赖。

**这个展开执行图，比原始计算 DAG 更接近最终优化对象。**

### 2. 我前一轮对全局存储门控的描述需要收窄

局部 Step3 确实按 allocation order 处理申请空间，但最终多核阶段不是重新维护同样的一套全局申请队列。

源码会把局部存储复用转换为额外依赖边，再让多核模拟器执行这些依赖。

所以正确的表述是：

> **局部申请顺序影响生成哪些内存复用约束；最终多核阶段受这些约束和固定 Pipe FIFO 控制。**

这不仅影响理论模型，也影响性能诊断。不能把所有空闲时间都解释成“当前没有剩余缓存”，有时真正限制执行的是已经生成的复用依赖。

另一个细节是：问题 2、3 输出的 `memory_peak_by_core` 取自局部 Step3。**要讨论实际多核时间线上的驻留峰值，需要独立重演，不能直接把这个字段解释成重新扫描全局执行得到的峰值。**

### 3. “子图图无环”还不足以保证方案最终可执行

我构造了一个四个计算操作的微图：原图无环，节点覆盖正确，分区校验也通过，但把同核顺序、Pipe FIFO 与跨核 COPY 合起来后形成等待环，最终被官方程序拒绝。

因此，团队必须区分：

**格式／分区合法**，以及**经过官方展开后可执行**。

不能把前一种状态写成“验证通过”。

这个机制也提供了一条算法方向：官方异常中带有具体的环边。可以利用它定位需要调整的局部顺序或分配，而不是候选失败后只随机重试。

### 4. 场景 B 的跨核多播，源端会按目标核心重复 COPY_OUT

这是一个不能用一般硬件常识替代源码的地方。

本版场景 B 的实现，对每个实际的“源核—目标核”连接分别插入 COPY_OUT／COPY_IN。**不是源端写一次，所有远端共同读取。**

我用一个 600-byte 中间张量送到两个远端核心做了测试：

| 相同数据关系 | 新增搬运量 |
|---|---:|
| 场景 A：源 Task 一次写出，两个目标分别读取 | 1,800 bytes |
| 场景 B：两个源核—目标核连接各有一对 COPY | 2,400 bytes |

这不意味着场景 B 整体更慢；微图中它仍因同步机制不同而更快。它意味着：

**通信代价必须匹配本版实际实现。不能直接把一个通用超图割代价当成准确成本。**

### 5. 问题 3 的搬运字段，不等于实际 DDR 服务流量

源码在 Cache 模拟之前就计算了 `data_movement_bytes`，随后原样输出。因此，固定方案在问题 2、3 下，这个字段可以完全相同，尽管部分读取已经走 Cache 而不是 DDR。

处理方式应当是：

**保留官方指标原值；另外统计实际 DDR 路径、Cache 路径及其字节数。**

不要为了让论文图表更符合直觉，悄悄修改指标定义。

## 三、已经有实验证据表明：单一路线会明显失效

我没有直接开发完整求解器，而是做了几种用于判断方向的构造。

“保守基线”保留计算依赖弱连通分量，按总计算量贪心分配，每核合成一个子图。

“小张量切分”尝试在极小张量连接处拆开结构，修复商图中的环后，再做块级分配。

“细粒度列表分配”以计算操作为单元，用简化的计算与通信代价进行调度。

下面都是**四核、场景 B、原样官方评估器的结果**，越小越好：

| 用例 | 保守基线 | 小张量切分 | 细粒度列表分配 |
|---|---:|---:|---:|
| `case_001` | 58,984 | 58,984 | 78,028 |
| `case_002` | 261,945 | 261,945 | 111,212 |
| `case_010` | 29,918 | 24,566 | 64,978 |
| `case_044` | 124,268 | 156,394 | 70,260 |
| `case_048` | 222,220 | 222,220 | 110,334 |
| `case_051` | 607,628 | 188,224 | 188,732 |
| `case_094` | 24,640 | 25,350 | 57,192 |

完整的 17 个用例对照保存在:chatgpt-content-reference{index="10"}:chatgpt-content-reference{index="13"}[预研证据包](sandbox:/mnt/data/NPU_A_Strategy_Codex_Handoff.zip)中。这些是简单的探测构造，**不是成熟强算法，也不是随机抽样的最终性能比较。**

但它们已经回答了几个重要问题。

**第一，保留整个计算分量有时很好，有时严重压缩并行度。**  
`case_051` 的改善非常明显，但这不意味着所有分量都应拆开。

**第二，小张量连接不是万能切分规则。**  
它帮助了 `case_010`，却没有解决 `case_002`、`case_048`，并且让部分用例变差。

**第三，细粒度调度有真正的价值，但不能无条件使用。**  
它改善了 `case_002`、`case_044`、`case_048`，却明显损害了 `case_010`、`case_094`。

因此，我建议最终采用：

> **少量候选构造＋基于结构与瓶颈的触发规则＋官方评估确认。**

这不是把十几个算法拼成一个大杂烩。它应当回答清楚：

**哪个候选解决哪种机制，何时值得启用，付出多少求解成本，以及为什么最终选中它。**

## 四、主求解器应该如何组织

### 1. 先建立正确的中间表示，避免三个决策互相混淆

内部至少应分别保存：

| 对象 | 用途 |
|---|---|
| 原始 Op–Tensor 图 | 张量来源、消费者、大小、位置、真实数据依赖 |
| 计算操作 DAG | 关键路径、就绪关系、分区合法性 |
| 子图划分 | 场景 A 的 Task 粒度，以及场景 B 的顺序分桶 |
| 操作／子图的核心归属 | 数据复用域与跨核通信 |
| 全局参考序与每核子图顺序 | 构造可控的局部顺序 |
| 展开后的执行图与时间线 | 最终可执行性、FIFO 等待、内存复用和瓶颈诊断 |

尤其不能把**子图编号、核心编号、阶段编号**当成同一个东西。

例如，同一份输入在两个阶段使用，可以把前后两阶段放到同核以争取复用，但仍保留为两个子图。不能因为希望同核，就把中间依赖外部归约的前后两段强行合成一个会产生商图环的子图。

### 2. 保留一个低风险基线，随后进行可中断改进

求解器启动后，先得到一个可信方案，再尝试更好的候选。任何新候选出现校验失败、等待环、异常或超时，都不能破坏已保存的合法结果。

这条规则看似工程化，实际上很重要：

**探索越激进，越需要有一个不会被探索破坏的当前最佳方案。**

但要注意：保守基线也不能永远只用“四核装箱”这一版。它必须支持题目要求的不同核心数量，并且经过全部用例验证。

### 3. 主候选一：结构与同步阶段感知的粗化

这条路线优先寻找：

重复分支、共享输入、长链、分叉—汇合、归约—广播、较小的数据接口，以及 Cube／Vector 工作量互补的区域。

这里不需要先猜“这是一种什么神经网络”。**真正进入算法的，应当是可检测的拓扑和张量属性。**

对问题 1，重点不是把每条分支都拆成一个 Task，而是联合决定：

**多少分支合成一批、归约部分放在哪里、需要多少层跨核同步，以及哪些独立工作可以一起交给一个 Task。**

题面规定问题 1 的同核 Task 切换等待和跨核前驱等待分别为 100、1,000 cycles；问题 2、3 的跨核 COPY 同步延迟为 500 cycles。这些固定等待足以改变细粒度切分是否值得。:chatgpt-content-reference{index="2"}

一个有价值的研究问题是：

> **能否根据分支工作量、接口大小与同步深度，推导或估计合适的批次粒度，而不是全体用例共用一个固定子图大小？**

### 4. 主候选二：考虑固定 FIFO 的分配与排序

这条路线作为独立挑战者保留，不要求它从结构路线出发。

它可以从较细的单元出发，综合考虑关键路径、各 Pipe 负载、跨核 COPY、共享输入以及内存压力，再进行列表构造和局部调整。

但成本模型必须逐步增加本题特有因素：

**不仅估计某项工作什么时候做完，还要估计它会不会挡住当前 Pipe 后面的工作。**

建议先做两个分离实验：

固定核心归属，只改变分桶和顺序；固定宏块划分，只改变核心归属。

否则，一个结果变好了，你们仍不知道真正有效的是切分、分核还是顺序。

### 5. 局部改进必须由瓶颈触发

不要无差别地随机移动节点。

当 Trace 显示主要问题是输入重复读取，就尝试聚合相关消费者；主要问题是一个核心的 Vector 长时间占满，就尝试拆分可并行分支；主要问题是跨核等待挡住 Pipe，就调整相关子图顺序或数据归属；主要问题是 SPILL，就缩短特定张量的驻留或改变粒度。

**一个局部修改，应当对应一个能够被前后时间线验证的因果解释。**

等待环也可以进入这个过程：把环边映射回引入它的分配或顺序决策，再做有针对性的修复。不能删除原始依赖、修改 validator 或把失败解释成“分数还没算出来”。

### 6. 评估缓存有价值，但缓存键不能过于粗糙

相同候选、相同材料和配置的评估结果应当复用。局部展开也可能缓存。

不过，**“操作集合相同”并不足以认定两个 Task 等价**：边界 COPY、子图顺序、实际 ID 与并列优先级都可能影响展开结果。

因此，精确缓存必须包含足够完整的上下文；粗略结构缓存只能用于成本估计，不能冒充正式评估结果。

问题 3 的全局 Cache 和共享带宽，又意味着局部 Task 成本不能直接相加得到最终 Makespan。

## 五、理论线应该从第一天开始，而且要有实际交付

你前面反复强调，不希望只是“现学一堆算法，再局部调参”。这道题确实可以用数学结构减少大量无效探索。

我建议理论线同时承担三个任务。

### 1. 下界：决定哪里值得继续投入

除了总工作量和关键路径，还可以利用操作的“最早开始时间”和“最长剩余路径”。

忽略通信和资源竞争，定义每个计算操作的 head 与 tail。对某一类 Pipe，取 head 不早于某个阈值、tail 不短于某个阈值的一组非空操作：

\[
\begin{aligned}
\mathcal U_p(\alpha,\beta)
&=
\left\{
v:
\operatorname{pipe}(v)=p,\;
h_v\ge\alpha,\;
q_v\ge\beta
\right\},\\[2mm]
T^\star
&\ge
\alpha+\beta+
\frac{1}{N}
\sum_{v\in\mathcal U_p(\alpha,\beta)}c_v,
\qquad
\mathcal U_p(\alpha,\beta)\ne\varnothing .
\end{aligned}
\tag{9}
\]

原因很直接：这些操作不能在前面的时间窗口开始前执行，也必须给后面的依赖计算留下时间；中间窗口内只有有限数量的对应 Pipe。

这是一种容量约束推导，不要求模拟所有调度细节。与其他合法下界取最大值，仍然是合法下界。

对于当前算法的可行结果：

\[
0
\le
\frac{T_{\mathrm{alg}}-T^\star}{T^\star}
\le
\frac{T_{\mathrm{alg}}}{LB}-1.
\tag{10}
\]

这就能给出前面提到的 `case_014` 的最优性差距上界。

需要把两件事明确区分：

**差距上界很小，是停止大量投入的有力依据；差距上界很大，却不证明一定存在巨大可实现收益，也可能只是下界太松。**

### 2. 结构压缩：把大量重复节点变成少量决策

对于结构和工作量相同的重复分支，可能不必一开始就分别搜索每个操作的位置，而是先决定每核承接多少条、如何分批，再重建具体方案。

这非常适合你们的强模型去研究，因为它可能直接降低决策维度。

但必须谨慎：**图结构看起来对称，不代表官方评估器对所有节点置换都严格不变。**固定 ID 的并列排序可能影响具体顺序。

所以在证明完成前，应当把这种压缩称为“构造方法”，而不是未经证明地宣称严格等价。

类似地，可以寻找接口较小的局部区域，在固定边界条件后研究动态规划或局部精确优化。不要一上来建立一个覆盖全部 Cache、带宽和执行顺序的巨大精确模型，然后让整队等待它。

### 3. 小图精确解：检验规则和算法，不只是展示漂亮案例

我已经做了一个四计算节点、两核微图的完整枚举：每问枚举 308 个分区／分配／顺序编码，经官方程序判断可行性，三个问题的最优值均为 64 cycles。

这个“最优”只适用于该微图，但它有明确用途：检查候选生成、合法性判断和性能解释是否正确。

后续应该扩展成覆盖不同机制的小图集，而不是只保留一个容易验证的例子。

**理论线的合格产物可以是一个新构造、一个下界证书、一类精确可解结构，或一个推翻错误假设的反例。不能把它降级成最后给已有代码补公式。**

## 六、L2 值得研究，但不应该提前成为整篇论文的中心

本轮全体固定方案对照得到：

**100 个四核保守方案中，29 个加入 L2 后 Makespan 下降，71 个不变；中位加速比为 1，最大约为 1.396。**

这是这组保守方案的观察，**不是 L2 优化的收益上限**。

它说明：不能仅凭“有较高共享输入比例”或者“Cache 命中率变高”，就判断最终时间一定显著下降。

另一方面，时序机制已经有一个很清楚的最小实验：

| 同一张图、相同核心分配，只调整两个独立子图的顺序 | 无 L2 | 有 L2 |
|---|---:|---:|
| 两核同时首次读取共享输入 | 333 | 333 |
| 其中一核先处理原图已有的独立工作 | 333 | 261 |

没有增加预取操作，没有插入任意等待，也没有修改配置。第一次读取完成后，后面的读取才有机会命中。

这符合题目规定的“COPY_IN 发射时查询、完成后插入”的机制；源码中也没有合并在途首次 miss 的处理。:chatgpt-content-reference{index="3"} 具体微图及官方运行结果见:chatgpt-content-reference{index="14"}[审计报告](sandbox:/mnt/data/npu_strategy_audit/AUDIT_REPORT.md)。

因此，L2 专项先回答四个问题就够了：

**哪些访问是真的重复读取？为什么没有命中？命中省掉的传输是否阻塞关键计算？为获得命中而调整顺序，会损失多少并行性？**

实验上保留“无 L2 优化方案”和“L2 专用方案”，分别在无／有 L2 下交叉评估。这样才能分清硬件收益、一般调度收益和真正针对 L2 的算法收益。

## 七、四台机器和 AI 资源，应当怎样分配

### 1. 人的职责不是传统的“建模／编程／论文”三分法

继续采用你偏好的组织方式：

**你负责模型、验收条件、研究优先级和最终判断；其他研究节点负责独立推进路线，交回能够比较的证据。**

论文写作从早期就记录模型、假设和证据，但不需要把某个人永久固定成“只写论文的人”。

四台机器也不是四个彼此独立的项目：

| 机器的初始角色 | 主要工作 |
|---|---|
| MacBook Pro：主控与研究汇总 | 共同模型、理论分析、接口审查、结果与论文主张 |
| 游戏本一：结构主线 | 阶段识别、粗化、同步粒度与相关实验 |
| 游戏本二：独立挑战线 | 分配、顺序、等待环与不同构造 |
| 游戏本三：验证与回归 | 原样评估器、固定基准、全量实验、干净环境复现 |

这只是初始分工。机器空闲后进入共享队列，不必等某个研究角色来使用。

**四台电脑用于研发并行；题目中的 2～5 个 NPU 核心是仿真对象，两者是不同层次。**

### 2. 先把独立实验运行好，不急着增加基础设施

目前实际发现的工作集中在 Python 图处理、核内展开与事件模拟。某些大型单核参考评估还有逐事件扫描带来的明显成本。

因此，第一步是测清楚 CPU、内存、输出序列化和评估热点，把独立实验分布到现有机器上。**本轮没有证据表明需要先上 GPU 训练或额外搭建复杂计算平台。**

你已有的 Agent 协议应当直接使用。不要在比赛期间再建一个通用调度产品，让基础设施反过来消耗比赛时间。

### 3. 最强模型要用在高影响的不确定性上

强模型持续承担源码合同、模型选择、理论推导、结构识别、失败分析和集成审查；低成本模型主要承担接口清楚后的实现、批量测试与记录。

但不要机械地规定“绝大多数工作都给便宜模型，强模型只用一点点”。**评价语义、实验设计和集成问题本身就需要强判断，不能按代码行数分配模型。**

与此同时，也不要让多个强模型反复吞入几百 MB 原始 JSON。

应该先由确定性程序提取所需视图，再按任务提供：

“这个结构的局部图”“这个张量的消费者”“这条等待环”“这一类用例的统计”“本次变更的对照结果”。

你已经在做的 Graph Engineering，在这里最有用的部分是**控制读取范围与证据依赖**，而不是让所有 Agent 都读同一份全量材料。

### 4. 研究优先级要考虑题面实际统计口径

题面要求先计算每个用例的加速比，再做算术平均，不是把所有时间相加后求比值。:chatgpt-content-reference{index="4"}

因此，同一核心数下，某个用例改善对平均加速比的贡献是：

\[
\Delta\overline S_{i,N}
=
\frac{T_i^{\mathrm{single}}}{100}
\left(
\frac{1}{T_{i,N}^{\mathrm{new}}}
-
\frac{1}{T_{i,N}^{\mathrm{old}}}
\right).
\tag{11}
\]

这不是评委完整评分规则，但它是明确的实验收益指标。

**不能因为一个大用例减少了很多绝对 cycles，就自动认为比一类中小用例的系统性改善更重要。**把指标贡献、下界所示空间、同类覆盖数量和验证成本一起用于决定下一轮投入。

## 九、实验纪律决定你们能否把“好想法”变成完整成果

### 唯一运行身份，防止不同结果互相覆盖

官方脚本有默认输出文件名。多核数、多场景、多算法并行时，直接沿用默认路径很容易覆盖结果。题面提供了显式指定结果、Trace 和日志输出路径的方式。:chatgpt-content-reference{index="5"}

每项实验必须记录：

**用例、问题、核心数、算法版本、参数、随机种子、材料／配置／代码／方案哈希、运行时间、状态，以及指标来源。**

不能让一个失败任务留下旧的成功结果，然后被汇总脚本误认为本轮成功。

### 所有内部搜索与选择成本都计入求解时间

题目建议单例在 5～10 分钟内给出结果，并明确希望避免暴力迭代搜索。:chatgpt-content-reference{index="6"}

研发阶段可以大量并行实验，用来发现更好的规则；最终算法则必须在自己的预算内运行。

**四台机器离线跑出来的最佳方案，不应当被包装成一个只运行几秒的算法结果。**

也不能把“从十几个候选中调用官方评估器选最优”的成本藏到算法外面。

### 先冻结比较规则，再看验证结果

正式阶段需要按结构族和规模组织开发与验证，不要仅按连续文件编号切分。

最终仍然要报告全部 100 个用例。当前预研已经看过全体结构摘要，后续不能再声称这些数据完全未见；但仍可以冻结算法与参数，让独立验证节点检查尚未用于调试的实例与机制。

平均成绩之外，保留逐用例结果、尾部退化和失败情况。**一个在多数用例上更好、但会在少数用例上失效的方法，必须有明确的处理机制。**

### 问题 3 的一核点也应当实测

问题 1、2 的固定单核基准及加速比定义不能换成你们优化过的单核结果。:chatgpt-content-reference{index="7"}

但问题 3 的一核 Cache 对照，也不能因为“只有一个核心”就机械填成没有收益：单核 SPILL 回读仍可能涉及 Cache。要按选定的对照口径实测，并与前两问的固定基准区分。

完整基本实验已有 **100 个用例、三问、2～5 核，共 1,200 组多核组合**，再加单核和消融。这个规模足以说明，实验工程不能拖到最后才开始。

## 十、什么样的成果值得作为冲击数模之星的主张

现在还没有依据判断最终排名；但可以明确，你们应当争取形成什么样的成果，而不是只追求“算法列表很长”。

我建议论文集中在三个能够守住的主张上。

### 主张一：把实际可执行性纳入联合建模

不仅考虑原始 DAG 和分区图，还考虑固定 Pipe FIFO、跨核依赖和内存复用边。

贡献可以体现为：更准确的模型、可执行的构造方法、针对等待环的修复，以及可复现的反例验证。

### 主张二：结构自适应的少量候选，比单一构造更稳定

重点不在“用了多个算法”，而在于：

**结构识别能否解释选择，候选之间是否解决不同瓶颈，选择成本是否受控，最终是否稳定改善完整测试集。**

前面那张对照表已经说明这个方向值得研究，但还没有完成这项主张所需的正式验证。

### 主张三：性能收益能够被下界和机制实验解释

对于接近下界的实例，说明已经受到什么资源限制；对于改善明显的实例，说明减少了哪类等待、复制或 SPILL；对于 L2，区分硬件收益和顺序优化收益。

**一篇能说明“为什么改善、何时无效、还能改善多少”的论文，比只给一个平均加速比和几张漂亮时间线更有研究内容。**

你们的 AI 调度体系，是获得这些成果的生产方式。它可以进入复现说明和工作流介绍，但不应替代题目本身的算法贡献。

# 二、建立正确的数学对象：先区分“编译”与“执行”

## 1. 真正可控制的变量

把我们的方案记为子图划分、核心归属和每核子图顺序。固定官方版本将其展开，再执行资源模拟：

$$\Phi_q(G,P,a,\pi;\kappa,\mathrm{IDs})
=
(H,\mathcal Q,\mathcal M,\mathcal S_0),
\qquad
T_q(P,a,\pi)
=
\operatorname{Sim}_q\!\left(\Phi_q(G,P,a,\pi;\kappa,\mathrm{IDs})\right).
\tag{R1}$$

这里：

- $H$ 是展开执行图；

- $\mathcal Q$ 是固定 Pipe FIFO；

- $\mathcal M$ 包含编译出的内存复用约束；

- $\mathcal S_0$ 是初始资源状态；

- 配置与 ID 规则不是我们的自由变量。

输出仍然只有 `node_to_subgraph` 和 `core_schedules`。**我们不能直接指定操作启动时间、任意插入等待、预取或重算，也不能用另一个理想核内调度器替代官方展开。**

通用神经网络处理器下的多核调度问题 +1

这是一类“**通过有限接口控制确定性编译器，再接受动态执行结果**”的问题。很多理论不能直接求解整个式（R1），但可以精确求解它的某个构造子问题。

## 2. 矩阵表示：保留生产与消费的区别

定义两个稀疏关联矩阵，**行是张量，列是操作**：

$$B^{p}_{t,o}=\mathbf 1[o\to t],
\qquad
B^{c}_{t,o}=\mathbf 1[t\to o],
\qquad
A=\mathbf 1\!\left[(B^c)^\top B^p>0\right].
\tag{R2}$$

因此，操作邻接矩阵 $A$ 的**行是后继操作、列是前驱操作**。它只表达依赖，不表达资源时间。

按官方 COPY 路径收缩口径得到非 COPY 操作依赖矩阵 $A_0$。令划分矩阵 $X$ 的行对应计算操作、列对应子图，每行恰好一个 1，则：

$$Q_{ij}
=
\mathbf 1\!\left[
i\ne j
\ \land\
(X^\top A_0X)_{ij}>0
\right].
\tag{R3}$$

这个 $Q$ 是商图。它没有包含新增 COPY、内存复用边、Pipe FIFO 和资源状态。

最终执行图还必须包含：

**原始数据依赖＋内存复用依赖＋Pipe FIFO 相邻边＋跨核 COPY 依赖**；问题 1 另有 Task 激活和完成约束。官方校验器确实在这些展开对象上继续检查，而不止检查商图。

## 3. 哪些通信代理可以精确，哪些不能

在当前场景 B 实现中，对**单生产者、非最终输出的中间张量**，跨核 COPY 是按不同目标核心各建一对。因此，在 SPILL 之前，其跨核搬运字节分量为：

$$D_{t,B}
=
2s_t
\left|
\{a(v):v\in \operatorname{cons}(t)\}
\setminus
\{a(\operatorname{prod}(t))\}
\right|.
\tag{R4}$$

这一式与普通“每条操作依赖边都收费”不同，也与“源端只写一次、所有消费者读同一份”不同。成员的多播微图与本轮旧微图复跑均支持当前实现的逐源核—目标核 COPY 对行为。

但必须限定：

**式（R4）可以准确计算一个字节分量，不会因此成为 Makespan。**原始输入按消费者核心去重，最终输出另算，SPILL 另算；问题 3 还必须区分计划中的 COPY 字节与实际走 DDR／Cache 的服务流量。

## 4. 谱方法的适当位置

Zhou、Huang、Schölkopf 的超图谱方法，以顶点—超边关联矩阵构造归一化 Laplacian：

$$L
=
I-D_v^{-1/2}HWD_e^{-1}H^\top D_v^{-1/2}.
\tag{R5}$$

这里 $H$ 的行是操作或宏块，列是共享张量 net；$W$ 是 net 权重，$D_e$ 是 net 基数，$D_v$ 是顶点加权度。

## 2. 数学观察：无环划分等价于某种“有序块”

一个集合是偏序的**理想集**，意思是：里面有某个操作，就必须包含它的所有前驱。

$$S\in\mathcal I(G)
\quad\Longleftrightarrow\quad
v\in S,\ u\leadsto v
\ \Longrightarrow\
u\in S.
\tag{R6}$$

下面这个命题直接决定算法表示。

**命题 A1。一个划分的商图无环，当且仅当存在原图的一条拓扑序，使每个分区块在该序中连续。**

证明很短。

正向：对商图拓扑排序，然后依次串接各块内部的拓扑序，即得到原图拓扑序。

反向：若各块在某个原图拓扑序中连续，那么跨块依赖只可能从前面的块指向后面的块，商图不可能成环。

其算法意义是：

> **与其搜索任意集合划分，可以搜索一串嵌套的前驱闭合集合；相邻集合的差就是一个有序块。**

但不能误读为“固定任意一条拓扑序，然后切连续段就没有损失”。命题说的是**存在某条序**。固定一条序会限制候选空间，这正是需要参数割来产生不同闭合集合的原因。

## 3. 构造一个精确可解、但明确是代理的切分目标

定义：

$$F_\lambda(S)
=
\sum_t c_t\,\mathbf1[0<|e_t\cap S|<|e_t|]
+
\sum_{v\in S}(d_v+\lambda w_v),
\qquad S\in\mathcal I(G).
\tag{R7}$$

各量的用途是：

**超边项**惩罚共享张量被切开；**正工作权重**控制选入多少工作；**固定一元偏好**可以鼓励关键路径上游工作、或者保留某些局部关系。

一个可落地的初版是：以正的 Cube／Vector 混合工作量作为工作权重，用归一化剩余关键路径给一元偏好，在少量固定的资源方向上扫描价格。

这里有一个必须主动防住的退化：

**若没有入／出锚点，而且一元偏好全为零，正价格选空集、负价格选全集。参数化本身不会自动产生有用切分。**

所以可以选择关键依赖链上的前后两个操作作为强制入／出锚点，或使用非平凡的一元偏好。锚点必须满足前驱闭包一致性；跨不同锚点的结果也不能冒称属于同一条嵌套参数路径。

### 最小割网络怎么建

用源侧表示选入集合。

对于原依赖“上游到下游”，在网络中加入**反向无限容量边**。下游被选入而上游不在，会切断这条边，因此被禁止。

每条超边增加两个辅助点：所有 net 内节点连向第一个辅助点，第二个辅助点连向所有 net 内节点，容量都取足够大的常数；两个辅助点之间连一条容量为该 net 代价的边。超边真正跨两侧时，恰好支付一次代价。

一元项通过源边或汇边表示。这样最小割**精确求解式（R7）**。它没有精确求解官方 Makespan。

## 4. 为什么参数扫描真的减少维度

**命题 A2。**在非负超边割代价、严格正工作权重、固定锚点与固定一元偏好下，价格增加时，最优理想集只会缩小。

设前后两次价格对应最优集分别为 $A,B$。理想集对交、并封闭；all-or-nothing 非负割函数是子模的。分别用交集、并集比较最优性，得到：

$$(\lambda_2-\lambda_1)
\sum_{v\in B\setminus A}w_v
\le 0,
\qquad \lambda_2>\lambda_1.
\tag{R8}$$

正权重迫使后选集合包含于先选集合。

因此，一条固定参数路径上的不同主节点集合，最多只有“节点数加一”种，而不是任意子集的指数数量。

**这就是结构性降维的核心。**不过，价格路径可能发生很大的跳跃，某个理想负载比例根本不出现。不能把这个结论包装成“平衡划分已经被多项式精确解决”。

令流网络的节点、边数分别为 $V_f,E_f$，价格查询次数为 $L$。初版重复 Dinic 的保守复杂度为：

$$\text{时间 }O(LV_f^2E_f),
\qquad
\text{空间 }O(V_f+E_f).
\tag{R9}$$

网络本身的规模与原依赖数、张量 pin 数线性相关。大型实现应使用紧凑残量网络，而不是把本轮小图 Python 原型直接搬到三万节点上。

参数复用还有一个细节：**“无限容量”必须在整段有界价格区间内固定且足够大**。改变内部容量、锚点之后，不能继续声称沿用了同一个参数网络的残量状态。

### 一个可以证明全局不会产生跨核环的安全特例

让每条计算依赖沿着**不下降的核心编号**传播，并且每个非空核只有一个子图。

在局部展开成功的条件下，所有跨核边都指向更大的核心编号；内存和 FIFO 边只在核内，所以全局不可能出现跨核等待环。

任一路径上的跨核次数至多为核数减一。这不是整体时间上界，但它限制了同步链的深度。

这个特例非常适合做低风险候选，代价也很清楚：**它不允许前后阶段返回原核心，可能损失跨阶段输入复用。**更一般的阶段划分允许重复使用核心，但必须恢复完整执行图检查。

### 失败机制与判别实验

最可能击穿这条路线的结构，是一个巨大共享输入连接所有并行分支，导致参数割在“几乎不切”和“切掉很多”之间跳跃；或者最佳方案需要前后阶段回到同核。

建议最小实验族是链、fork–join、两轮共享输入。对照三个构造：无方向 net-cut 后修环、固定拓扑序连续切分、理想集参数切分。

成功依据不是“非法率降低”本身，而是：

**在相同端到端预算下，更少 E0 调用能否找到不差甚至更好的方案。**若只是产生更安全但持续更慢的结果，应将它降为初始解构造，而不是维护为主算法。

## 2. 从逐分支身份，变为每核数量

若有一类真正可交换的重复分支，分配到有标号核心：

$$(n_1,\ldots,n_N),\qquad
\sum_{k=1}^{N}n_k=m,
\qquad
N^m
\longrightarrow
{m+N-1\choose N-1}.
\tag{R10}$$

这个压缩非常大，但右侧也并非永远小。几千条分支、五个核心时，不能照样枚举所有计数组合；应按类型做数量 DP，或者只生成资源平衡附近的计数构造。

### 什么条件下计数化严格成立

仅要求原图同构不够。

**一个充分条件是：**两种分配的展开操作与张量之间存在双射，并且保持：

固定 Pipe FIFO 位置、计算和 COPY 工作量、数据边和内存边、Cache key 的相等关系、核心编号、同刻事件优先关系及初始状态。

在这个条件下，可按官方的 settle、retire、issue、advance 顺序逐步归纳：对应状态和下一事件保持一致，最终 Makespan 相同。

这个条件看起来强，正是因为本题有固定 ID 和确定性并列规则。**我们希望逐渐找到容易检测、足以推出该条件的结构特例，而不是把“哈希相同”当成证明。**

### 本轮已经得到一正一反两个实例

五条独立私有分支，分别包含 60-byte COPY_IN、100-cycle RELU、60-byte COPY_OUT。两核、每核一个子图。

按核心 0 的分支数量从零到五，32 种分配归类后的 Makespan 分别为：

**502、403、303、303、403、502 cycles。**

每个计数组内完全一致。

但另一组分支局部操作标签相同，其中只有一条为后续 800-cycle 操作提供输入。相同计数交换身份后，时间由 **823 变为 1326 cycles**。

所以，分型签名至少要包含：

**操作／Pipe／cycles、张量大小与位置、内部结构、外部消费者关系、阶段位置。**原 ID 的具体实现差异则要保留为待验因素；不能修改原图 ID 来制造对称性。

## 3. 没有完全重复时，用窄边界状态代替全历史

取一条合法参考拓扑序，逐步处理其前缀。只保留那些“已经涉及，但未来还会使用”的张量，作为 frontier。

重要的是：**共享原始输入也要进入 frontier**，不能只看计算依赖图的弱连通分量。

一个明确可实现的状态为：

$$\mathcal Z_j
=
\left(
(p_t,C_t)_{t\in F_j},
(L^M_k,L^V_k)_{k=1}^{N},
D_j
\right).
\tag{R11}$$

含义如下。

**张量生产核心**记录数据来自哪里；**消费者核心位掩码**记录哪些核心已经为它付出一次读取或跨核 COPY；**Pipe 负载向量**记录每核 Cube 与 Vector 工作量；最后一项记录已结算的通信代理成本。

最后一项是同一状态键保存的最优标签，不必作为额外穷举维度。

处理下一个操作时，只需要枚举核心归属：更新它涉及张量的位掩码，第一次出现远端消费核心时计入对应通信；张量完成末次涉及后，就可以从状态中删除。

这给出了一个真正的“遗忘”原则：

> **只要未来所有代价都只依赖保留的边界状态，过去内部身份就可以被消去。**

对于固定拓扑构造、单生产者、SPILL 之前的场景 B COPY 字节和累计 Pipe 工作，这一原则可精确定义；对于完整官方 Cache、驻留与执行顺序，则不能省略相应历史后仍称精确。

## 4. 复杂度和停止条件必须写出来

设最大 frontier 张量数为 $b$，两类总计算工作上限为 $U_M,U_V$。不量化整数负载时，一个保守状态数上界为：

$$H
\le
\bigl((N+1)2^N\bigr)^b
(U_M+1)^N(U_V+1)^N.
\tag{R12}$$

它直接说明：**小核心数不自动使问题容易；边界宽度与负载状态仍可能爆炸。**

以实际保留状态数 $H$、每操作涉及张量数 $d$ 估计，采用数组状态与哈希表：

$$\text{时间 }
O\!\left(nNH(b+d+N)\right),
\qquad
\text{滚动状态空间 }
O\!\left(H(b+N)\right).
\tag{R13}$$

完整回溯还需要父指针存储；可以通过检查点与重算控制内存，但重算必须计时。

在**相同边界状态、相同负载向量**下只保留最小通信标签，是该代理上的安全剪枝。量化负载、限制 beam 或仅保留若干 Pareto 点，则成为启发式，不再具有精确性。

尤其不能在问题 3 中直接使用“更早、搬运更少就支配另一状态”的规则：它们可能形成不同 Cache 顺序，从而产生不同后果。

### 适用范围与证伪

# 五、路线 C：max-plus 端口消元，以及从 FIFO 阻塞构造局部修改

这条路线包含两个层次：**精确压缩固定时延部分**，以及**利用实际阻塞关系缩小排序改动范围**。

## 1. 文献基础与适用条件

**L5：**François Baccelli, Guy Cohen, Geert Jan Olsder, Jean-Pierre Quadrat，*Synchronization and Linearity: An Algebra for Discrete Event Systems*，Wiley，1992，ISBN 0-471-93609-X。[作者开放版入口](https://www.rocq.inria.fr/metalau/cohen/SED/book-online.html?utm_source=chatgpt.com)，[本轮实际阅读的 Delft PDF](https://repository.tudelft.nl/file/File_681d1849-7274-4560-a103-aeb57d4d87ee?utm_source=chatgpt.com)。

读了 Chapter 3 的 Theorem 3.17／3.20、矩阵路径解释和相关闭包。这里适用的是固定依赖、固定时延的最早事件系统；**不把最大环均值当成有限 DAG 单次执行的 Makespan，也不把动态 DDR／FIFO Cache 整体称为 max-plus 线性。**[[图片：]TU Delft Repository+1](https://repository.tudelft.nl/file/File_681d1849-7274-4560-a103-aeb57d4d87ee)

## 2. 把计算内部变成“端口响应”

在官方展开完成后，将操作拆成开始与结束事件。计算时长、固定同步、数据边、内存复用边和 FIFO 边中的固定部分，构成固定时延图。

保留以下端口：

**动态 COPY 的开始与完成、Cache 查询与插入、外部释放、Task 门控，以及零时刻常数端口。**

只消去没有动态资源副作用的内部事件。

令矩阵的行对应目标事件、列对应源事件，边权为固定延迟；缺边取负无穷。max-plus 的“加法”取最大值，“乘法”取普通加法：

$$x=A\otimes x\oplus b,
\qquad
A^*=I\oplus A\oplus\cdots\oplus A^{r-1}.
\tag{R14}$$

因为固定部分是 DAG，闭包有限。

把节点分为边界端口和内部节点，消去内部后得到：

$$K
=
A_{BB}
\oplus
A_{BI}\otimes A_{II}^*\otimes A_{IB}.
\tag{R15}$$

这就是一个**端口到端口的最早时间响应矩阵**。

### 可以证明什么

**命题 C1。**若内部节点没有额外外源释放或动态状态，固定整数时延图采用式（R15）消元后，对任意给定的端口释放向量，所有端口的最早时刻保持不变。

证明：每条穿过内部节点的端口间路径贡献其延迟之和；闭包对这些路径取最大值，恰好保留“全部相关前驱都满足后才能继续”的约束。

这不是普通 Schur 补或无向 Laplacian 的 Kron reduction。那些运算保留的是另一类线性响应；本题“等全部前驱”对应的是最大值，不是普通求和。

还有一个有限的支配规则：在**同一端口语义、同一非动态单调后续网络**中，一个响应矩阵逐项不大于另一个，就不会给出更晚输出。可是涉及动态共享带宽或 Cache 时，不能直接升级为原题的安全支配。

## 3. 成本与数值边界

一个内部区域有 $r$ 个节点、$e$ 条边、$b$ 个端口，可以从每个端口做 DAG 最长路：

$$\text{预处理时间 }O\!\left(b(r+e)\right),
\qquad
\text{响应存储至多 }O(b^2).
\tag{R16}$$

当端口较少、内部链或局部结构很大时有价值；若大量 COPY 遍布区域，端口可能和原节点同阶，消元产生 fill-in，反而不合算。应当按边数膨胀预算停止。

**一个特别重要的精度边界：整数固定部分的数学等价，不等于 E1 零差分。**

官方会在事件点用 binary64 结算带宽剩余工作。消去中间计算完成事件，可能改变浮点运算分组，进而改变 `ceil` 附近的结果。端口引擎必须保留这些结算效果，或者先作为 E2／筛选器，不能仅凭实数代数正确就宣称 E1 一致。

完整 Trace 也要一致重建；不能用端口引擎的 Makespan 拼上另一引擎的旧时间线。团队补充规范明确禁止这种混拼。

## 4. 如何产生更好的方案，而不只是更快评估

新 FIFO 夹具提供了一个很具体的构造入口。

核心 1 上的 M 管道操作在第 12 cycle 完成，后续一个独立 V 操作的数据已齐。但是 V 队首是另一个等待远端数据的操作，导致这个独立工作直到第 609 cycle 才启动。

只交换两个合法子图的顺序，独立工作就从第 12 cycle 开始，最终 **1410 降到 818**。搬运量、核心归属、原操作完全不变。

这说明应该寻找的不是抽象的“更优排序”，而是：

> **哪些可控制的子图顺序，正在把一个远端等待传播为本核无关工作的等待？**

源码中的 `pipe_cursor` 检查确实要求当前操作是固定队首；这比“同 Pipe 串行”更强。成员原报告明确没有覆盖这种越过性，本轮新图独立补充了这一行为。

## 5. 一个值得保留的跨领域加速构想：虚拟服务时钟

对单个公平共享带宽池，所有正剩余请求在同一时段获得相同服务。可以引入虚拟服务时钟：

$$V(t)
=
\int_0^t
\frac{\mathbf1[n_{\mathrm{pos}}(u)>0]}
{\max(1,n_{\mathrm{pos}}(u))}\,du,
\qquad
f_i=V(a_i)+w_i.
\tag{R17}$$

这里，工作量使用官方已经取整的独占带宽参考周期。请求的剩余工作可由固定虚拟截止值减去当前虚拟时钟表示，从而避免每次事件都逐项扣减全部请求。

这是对官方等分服务方程的坐标变换，不是把全局耦合拆成独立核心。

**它尚未实现。**连续服务完成与整数 cycle 的 retire 必须区别；EPS、`ceil`、同刻 Cache 处理、浮点运算顺序也要另验。而且五核时在途 COPY 总数至多十个，实际可能是小数组比堆更快。

因此，这是一个可能与端口压缩配合的数学内核，不是已有 E1 加速成绩。

# 六、增量失效与安全剪枝：哪些局部性是真的

## 1. 不默认“移动一个子图只影响两核”

一个小修改可能依次改变：

**边界 COPY 数量与生成 ID → Step1 并列顺序 → SPILL 与重命名 → 内存额度来源 → Pipe FIFO → 全局 DDR 完成时刻 → Cache 插入次序 → 其他核心的命中与启动。**

因此，局部编译结果的缓存键不能只有“这组操作 ID”。至少还要包含边界上下文、子图顺序、生成 ID 规则及会影响并列的内容。

可以安全复用的，是完全相同上下文的编译结果，或者固定执行图中不含动态副作用的响应算子。

**精确拼接一个旧执行后缀的充分条件**是：在切点处，完整离散状态、剩余工作、浮点池状态、FIFO Cache 的有序内容，以及未来队列和映射一致。只有“两核空闲”“总剩余字节一样”远远不够。

## 2. 从失败环得到修复，不等于得到任意泛化的禁用规则

失败环很有价值，因为它指出冲突来自哪条 FIFO、跨核或内存边。

但只能修改可控的分组、归属、顺序，不能删除原依赖或关闭校验器。

对**整份失败方案**做去重和禁用是安全的；若想把环归纳成“只要出现这三个分配决定就永远非法”，必须证明这些决定足以强制产生相同展开边。固定 ID 与内存额度的上下文依赖可能使这个归纳失效。

## 3. 下界要分清“原问题”和“固定候选”

仍建议保留前轮的计算工作量、关键路径与头尾窗口下界。

忽略通信，设前置计算最长时间与后续计算最长时间给出头、尾。对于同类 Pipe 上的一组操作，若它们都不能早于某个头阈值开始，又必须留下某个尾阈值：

$$T^\star
\ge
\alpha+\beta+
\frac{1}{N}
\sum_{v\in U}c_v.
\tag{R18}$$

证明是容量窗口：这些工作必须放进同一个中间时间窗口，而该类 Pipe 总共只有有限条。

对当前合法解：

$$0
\le
\frac{T_{\mathrm{inc}}-T^\star}{T^\star}
\le
\frac{T_{\mathrm{inc}}}{LB}-1.
\tag{R19}$$

前轮存档中某些大实例已经有较小差距上界，这仍是减少无效搜索的依据；但本轮没有全体重算这些证书。

必须区别三类值：

| 数值 | 可以怎么用 |
| --- | --- |
| 对所有合法方案成立的资源／依赖下界 | 原问题质量证书、研究投入判断 |
| 固定候选展开图的乐观最长路 | 该候选的筛选或解释 |

本轮没有运行 CUDA 或 Metal；没有测本队设备。

尤其不能把“支持 64 位整数”理解为“适合原生双精度事件模拟”。完整 MSL 规范 PDF 本轮获取未成功，因此不引用未核实的 FP64 条款；稳妥设计是先让整数图内核可选上 GPU，把 binary64 带宽池留在 CPU。

## 2. 真正值得试的，是压缩后规则化的批量，而不是逐事件上 GPU

| 计算部分 | 有竞争力的 CPU 实现 | CUDA／Metal 的合理位置 |
| --- | --- | --- |
| 张量关联扫描、核心位掩码、批量负载统计 | 紧凑 CSR／CSC、SIMD、多核候选并行 | 同图驻留、候选足够多时尝试 |
| 同形整数 max-plus 响应 | 小矩阵／稀疏数组、缓存内计算 | 多候选同拓扑批处理 |
| 分层 DP 的大量相同转换 | 连续状态数组、哈希去重 | 层内并行；层间同步与去重成本必须计入 |
| 不规则最大流 | C++ 紧凑残量网络、网络复用 | 不预设 GPU 更快；分支和不规则访存较重 |
| Step1、SPILL、虚拟额度 | 稳定排序、未来使用索引、局部数组 | CPU 优先 |
| 单候选 DDR／Cache 事件循环 | 最多十个在途 COPY 的小数组 | 每事件启动 kernel 通常缺少足够并行工作 |
| 大量完整候选模拟 | 多核 CPU 批处理 | 可研究开发吞吐，但不能替代单例端到端测量 |

这是本轮的执行设计判断，依据是实际算法的依赖结构，而不是硬件型号宣传。

### 数据布局

原 ID 与稠密数组下标分开；操作属性使用结构分离数组；前驱、后继用紧凑 CSR／CSC；消费者核心集合用小位掩码；整数时间使用检查溢出的 64 位表示。

多候选共享只读图，候选差异用核心标签、分桶顺序、数量参数表达。GPU 上可把“候选维度”连续排列，让同一操作或同一端口在一批候选上的访问合并；不要为每个候选复制完整 Python 对象图。

NVIDIA 官方 Best Practices 对访存合并、传输最小化和 profiling 的要求支持这种布局方向。CUDA Graphs 可以摊销重复短任务的启动，但实例化与同步也要计时；**CUDA 的命令图不是赛题执行图的替代品。**[[图片：]NVIDIA Docs+1](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)

### 不为 Tensor Core 或 Neural Accelerator 硬造矩阵乘

max-plus 使用“最大值与加法”，不是普通 GEMM 的“加法与乘法”。原生整数最大流也不是神经网络矩阵乘。

Apple 官方 Metal tensors 讲解的矩阵乘、卷积加速路径不能直接当作这些内核的加速证明。采用 log-sum-exp 等近似来强行映射，还会引入新的目标与数值误差，不适合精确构造线。[[图片：]Apple Developer](https://developer.apple.com/videos/play/wwdc2026/330/)

## 3. 可测的盈亏点，而不是凭峰值算力判断

对同一图的若干个**新候选**，可以用：

$$\begin{aligned}
T_{\mathrm{CPU}}&=P_C+Kc_C,\\
T_{\mathrm{GPU}}&=P_G+L_{\mathrm{launch}}
+\frac{D_{\mathrm{transfer}}}{B_{\mathrm{link}}}
+Kc_G+T_{\mathrm{sync}}.
\end{aligned}
\tag{R20}$$

把固定额外成本合并后，只有单位候选 GPU 成本更低且批量超过盈亏点才有意义：

$$K>
\frac{F}{c_C-c_G},
\qquad c_C>c_G.
\tag{R21}$$

例如，**假设而非实测**：CPU 每候选 80 微秒，GPU 10 微秒，附加固定成本 200 微秒，至少三个候选才可能回本。真实传输、去重、编译和 E0 确认成本可能让结论完全改变。

应该分别测批量 1、16、64、256，冷／热启动，内核／完整 CLI，开发吞吐／最终单例。Mac 统一内存也不能消除同步和带宽竞争。

**数学压缩成功后，候选数和图规模变小，GPU 反而可能失去优势。这是算法成功，不是硬件路线失败。**

## 4. 确定性与 CPU 回退

整数 max-plus 使用安全的负无穷哨兵和溢出检查；不能让 FP32 承载所有大整数时刻。浮点池必须保留 EPS、`ceil`、事件顺序和运算分组；不能打开改变语义的 fast-math 后仍称 E1 零差分。NVIDIA 的浮点文档也明确区分舍入、FMA 和不同执行路径。[[图片：]NVIDIA Docs](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/mathematical-functions.html)

无 GPU、SDK 不匹配、批量过小、图过窄、端口过密或精度未验收时，直接使用 CPU。**CPU 不是补救方案，而是这道不规则离散事件问题必须认真比较的主路线。**

在首组 7 个正式用例上，它没有超过旧三个构造的最好值。`case_002` 的构造约耗时 **5.75 秒**，最终 **115746 cycles**，明显不如下面的串行包路线。

这否定的是**当前这一版切分代理与构造方式的优先级**，不是否定理想集理论。源码、参数、结果都保留了，不因为它曾被推荐而继续扩大投入。

### 全局事件消元也暂时不作为前置工程

上一轮的 max-plus 端口消元，需要继续解决动态带宽、Cache、浮点结算与完整输出问题。

这轮选择了一个更直接的落点：

> **先把 max-plus 用在候选构造中的计算资源响应，不尝试替换官方事件模拟器。**

这样，数学压缩仍能帮助决策，却不需要先证明一个新评估器与 E0 全域等价。

DAG 聚类本身并不是新发明。例如 Yang、Gerasoulis 的 DSC 就研究聚类与调度，但背景是无界、完全连通处理器，其结论不能直接移植到本题的固定核数、共享 DDR 与固定 FIFO。这里的研究重点应当是本题特有的构造与验证，而不是把已有聚类思想重新命名。:chatgpt-content-reference{index="4"}

## 三、主构造：归属粗化，执行细化

这条路线最重要的区分是：

**“哪些操作应该留在同核”与“哪些操作应该永远放在同一个子图里”，不是同一个问题。**

前者保护数据复用；后者影响官方编译出的顺序。把两者绑死，会损失流水交错机会。

### 1. 先找可以安全收缩的串行包

在正确收缩 COPY 后的计算 DAG 中，只粘合满足以下条件的边：

\[
u\to v,\qquad
\deg^+(u)=1,\qquad
\deg^-(v)=1.
\tag{S1}
\]

所选边形成无分叉链。链的内部计算节点不会被外部计算依赖从中间插入，也不会从中间分叉出去。

**这个收缩保持计算商图无环。**若收缩后出现环，就能沿每条链内部的有向路径，把它还原为原计算图中的环，与原图为 DAG 矛盾。

但这个命题只保证**计算商图**。新增 COPY、Pipe FIFO、内存复用边仍由官方展开决定，不能把它升级成完整执行可行性保证。

原型还做了一项保护：先比较自己使用的计算邻接与官方 COPY 收缩邻接。遇到尚未支持的内部 COPY 桥接，会明确报不支持，不悄悄漏掉依赖。

### 2. 用小矩阵代替“包的总 cycles”

一个包如果包含不同 Pipe 上的操作，单个总工作量不能描述它如何占用 Cube／Vector。

本轮用三个输入时钟描述一个计算包：旧 M 时钟、旧 V 时钟，以及包外输入的共同释放时刻。输出为更新后的两个 Pipe 时钟和包完成时刻：

\[
\begin{bmatrix}
M'\\V'\\C
\end{bmatrix}
=
K_B\otimes
\begin{bmatrix}
M\\V\\r
\end{bmatrix},
\qquad
(K\otimes x)_i=\max_j(K_{ij}+x_j).
\tag{S2}
\]

矩阵的行、列在这里有明确含义，不是把图转成矩阵后随便求一个特征值。

构造方法也很直接：按规定的包内计算顺序，每个操作等待同 Pipe 前项、数据前驱与共同释放，再加上计算周期。每个完成时间始终是“三个输入加常数，再取最大值”的表达，因此能压成一个 **3×3 响应矩阵**。

**这个表示对固定计算 FIFO、共同输入释放的子模型是精确的，对官方完整 Makespan 不是。**它没有包含真实 DDR 等分争用、SPILL、内存额度来源、Cache，以及不同输入各自的到达时刻；也不是原问题下界。

在 `case_002` 中，**1798 个非 COPY 操作变成 397 个核心归属包，只有 3 种不同的计算响应矩阵**。

这里不能再过度压缩：397 个包仍保留各自的张量接口、原 ID 和依赖位置。**共享三种响应函数，不等于原问题只剩三个实体。**

### 3. 在宏图上决定核心归属

构造器按剩余计算路径生成宏块的共同拓扑参考序。对每个包，尝试各核心，估计：

- 输入到达与跨核等待；
- 该核 M／V 两个时钟的变化；
- 同一输入是否已被安排在该核读取。

然后选取一个核心，更新资源状态。

这是一个有意简化的构造代理。比如“已读取集合”目前不包含完整的容量与淘汰过程，不能解释成真实驻留集合。**最终每个候选都由原样 E0 判断。**

复杂度主要是图扫描、拓扑排序，以及每包尝试少量核心；没有枚举全部分配，也没有要求先训练成本模型。

## 四、真正有效的第二步：固定核心归属，再改变子图与顺序

### 1. 一个有用的实现级不变量

对于问题 2、3 的冻结构图，保持每个操作的核心归属不变，就保持了张量的生产核心、消费者核心和跨核 COPY 配对集合。因此：

\[
a_1(o)=a_2(o)\ \text{对所有操作成立}
\quad\Longrightarrow\quad
D_{\mathrm{partition},1}
=
D_{\mathrm{partition},2}.
\tag{S3}
\]

这里指的是 **SPILL 之前的切分新增搬运分量**。

证明按张量分别检查即可：原始输入的读取核心集合不变，中间张量的源核—目标核集合不变，最终输出的生产核心不变。

但必须保留三个边界：

**SPILL 量不一定不变；Cache 实际路径不一定不变；Makespan 更不一定不变。**问题 1 跨子图也需要 DDR 中转，因此不能套用这个不变量。三问的 Task 组织差异正是题面规定的。:chatgpt-content-reference{index="5"}

这个不变量让我们能把实验拆开：**先优化数据归属，再观察仅改变顺序能带来什么。**

### 2. 资源重入，是值得拆包的位置

考虑一条链先用 M、再用 V、随后返回 M。

把整条链放在一个子图里，官方可能把它的两次 M 使用都排在同 Pipe 的其他独立工作之前；中间等待 V 的时间就浪费了。

本轮做了一个使用原配置的公开输入微图：

| 相同图、相同核心、相同搬运统计 | 问题 2 | 问题 3 |
|---|---:|---:|
| 整条链保持一个子图 | 204 | 204 |
| 在返回 M 前拆开，让另一条独立 M 工作插入 | **104** | **104** |

链是 M1→V100→M1，另一条独立工作是 M100。没有增加等待、预取或重算；自动构造也复现了对应结果。

**这给出了一个明确反例：保持商图无环的安全粗化，仍然可能损害性能。**

### 3. 用有限参考窗口组织阶段交错

进一步，把粗包按连续同 Pipe 段拆开。在粗包的共同拓扑参考序上，选取一个有限窗口；窗口内按阶段索引和原包位置组织细包，再投影为各核子图顺序。

伪代码可以压缩为：

```text
先构造粗包分核方案
冻结每个原操作的核心归属

将粗包拆成连续同 Pipe 的阶段
对少量固定参考窗口：
    生成满足依赖的阶段拓扑序
    投影为各核的子图顺序
    输出原操作 ID 的 node_to_subgraph
    调用官方评估器
    保留已确认合法的最好方案
```

**参考窗口不是物理屏障，也不是实际并发包数或存储峰值的上界。**官方仍可能提前搬入后续数据。我们控制的只是允许提交的子图与顺序，不是执行时钟。

## 五、正式用例的收益与失败，已经可以分开解释

### 1. `case_002` 的消融说明：主要收益不是一个“高级矩阵名字”

以下均为本轮 E0 新结果，问题 2、四核：

| 构造 | Makespan |
|---|---:|
| 旧三个探测构造中的最好值 | 111212 |
| 使用同一新成本模型，但仍逐操作分配 | 104109 |
| 串行包，仍用标量计算成本 | 72650 |
| 串行包，使用两 Pipe 矩阵响应 | 71904 |
| 固定核心归属，按资源重入细化 | 71108 |
| 固定核心归属，32 包参考窗口细化 | **66376** |

这说明：

**第一层主要收益来自“哪些中间数据不应被轻易切到其他核心”。**旧逐操作方案的新增搬运为 5,078,016 bytes，链包方案降到 743,424 bytes。

**矩阵响应贡献了一部分额外改善，但不是全部改善。**在相同链包构造下，72650 到 71904 约改善 1.03%。

**最后的顺序改善与搬运改善可以分离。**71904 到 66376 的五项搬运统计完全相同，且都没有 SPILL，时间下降约 7.69%。

这些方案与完整结果在:chatgpt-content-reference{index="16"}[实验表](sandbox:/mnt/data/NPU_A_Structural_Prototypes_R3/analysis/RESULTS.md)中；关键结果还通过随包重新解压的官方原件，做了完整 JSON 复跑对照。

这个用例也能给出一个简单但严谨的质量证书：总 M 工作量为 240000 cycles，四核至少需要 60000。因此：

\[
T^\star\ge60000,
\qquad
0\le
\frac{66376-T^\star}{T^\star}
\le
\frac{66376}{60000}-1
\approx10.63\%.
\tag{S4}
\]

这是相对真正最优值的**差距上界**，不是证明 60000 可达，也不是说已经求出了最优解。

### 2. 另一组用例否定了“统一换成新构造”

在运行前列出的 8 例中，固定比较旧三个构造与两个新基础构造，不在组内看到结果后调参：

| 用例 | 旧三构造最好 | 新二构造最好 | 判断 |
|---|---:|---:|---|
| case_019 | 23219 | 23219 | 相同 |
| case_026 | **28637** | 29824 | 新构造退化 |
| case_037 | 53320 | 53320 | 相同 |
| case_064 | 15035 | **14900** | 改善 |
| case_069 | 20835 | **17707** | 改善 |
| case_071 | 15328 | **13443** | 改善 |
| case_080 | **107695** | 111314 | 新构造退化 |
| case_096 | 24913 | **23073** | 改善 |

结果是 **4 改善、2 相同、2 退化**。这是预列验证组，不冒称这些 case 在全部历史讨论中完全未见。

因此，正确的交付不是“用新方法替换旧方法”，而是**保留少量机制不同的候选，用真实评估确认选择**。这个选择成本必须计入求解时间。

### 3. 窗口越大，也不一定越好

`case_044` 的原链包方案是 **74838 cycles**。固定相同核心归属后，参考窗口分别取 8、32、128 个包，得到：

**76410、89524、105715 cycles。**

五项搬运统计仍然相同，也都没有 SPILL。扩大窗口导致明显退化，不能解释成容量溢出，更不能根据“理论并行空间更大”判断它一定更快。

后续把固定窗口参数转移到另一组 7 例，相对原链方案是 **1 小幅改善、2 相同、4 退化**。所以窗口细化应当是**有条件触发的候选**，不应无条件应用。

### 4. 问题 3 和核数变化都已做有限转移检查

这不是仅在一个微图上工作的机制：

`case_002` 两核时，旧构造最好为 138426，固定归属窗口方案为 **126586**；五核时，旧构造最好为 117925，窗口方案为 **57102**。

但问题 3 会改变优劣关系。`case_044` 在问题 3 下，旧逐操作方案为 **63765**，新重入构造为 64945，窗口方案为 84126。**问题 2 的改善不能照抄为问题 3 的改善。**

本轮主构造实验共 **293 次 E0 调用，覆盖 15 个正式 case**，每次完整结果均保留。这是调用数，不是 293 个独立样本，也不是全体 100 例的最终成绩。

## 六、问题 1 要另处理：合法合并还必须保护 Task 的释放时机

问题 1 每个子图就是独立 Task。过细的阶段拆分会引入 Task 等待，因此不能把问题 2 的方案直接照搬。

本轮实现了一个精确的**合法合并检查**：

在 Task 数据依赖图上，加上每核相邻 Task 的顺序边。对相邻同核 Task 的直接边进行收缩，保持 DAG 的条件是：

\[
\operatorname{contract}(A,B)\text{ 后仍为 DAG}
\quad\Longleftrightarrow\quad
\text{不存在经过其他节点的 }A\leadsto B\text{ 路径}.
\tag{S5}
\]

这是偏序中的覆盖关系。收缩产生的新环，恰好对应这种替代路径；每次合并后重新检查全局关系，而不是假定只影响两核。

**但合法性不等于收益。**

本轮构造了一个非常直接的反例：核心 0 的短操作 A 产生远端长任务 C 的输入，A 后面还有本核独立长任务 B。

| 方案 | 问题 1 Makespan |
|---|---:|
| A、B 分开，C 尽早被释放 | **6014** |
| 合法地合并 A、B | 11005 |
| 加入远端出口保护，不执行这次合并 | **6014** |

搬运统计相同，差别来自：**C 原来只需等待 A，合并后必须等待整个 A+B Task 完成。**

正式用例也体现了这种条件性：`case_002` 的链包种子为 122820，受保护合并后降到 **93126**；但 `case_051` 从 338092 合并成 385092，反而变差。

所以这条路线目前应当作为**有出口／输入门控意识的少量合并候选**，不应写成“Task 越少越好”。

## 七、真实 E1/E2 的新检查，进一步支持“小候选＋E0”路线

本轮把真实 `3357d7e` 实现放到了新构造上，而不只引用队长旧报告。队长报告原本就明确：有限正确性检查不等于性能验收，问题 2、3 尚未覆盖。

| 检查 | 本轮新观察 | 不能外推的结论 |
|---|---|---|
| 5 个问题 1 小池、40 次 E0/E1 完整对象比较 | **40 次均无差分**；按写出方案哈希去重为 37 份 | 不等于全输入域等价 |
| 三例各预热一对、正式三对 API 计时 | 约 **1.85×、1.27×、1.48×** | 不是完整 CLI 倍数，仍未达到 3×门槛 |

此外，在这些每池 8 条记录的诊断池里，若只取 E2 事件估计的第一名，会在 `case_002/010/026` 分别丢失约 **6.52%／26.27%／21.30%** 的池内最好成绩。排序路线在 `case_002` 也有约 6.52% 的损失。

据此，本轮主算法没有让 E2 决定哪些结构候选永远不进入 E0。**用数学结构先把候选数压小，比现在依赖一个误差仍大的代理去大规模筛选更可靠。**

## 八、已经做成可独立运行的原型，不只是候选成绩表

`src/solve.py` 会从原图生成有限候选，调用**原样官方 CLI**，保存每次完整结果、Trace、日志，再选取已确认合法的最好方案。

它不依赖 LLM 服务，不使用隐藏的离线答案，也不会拼接 E2 的 Makespan 与另一引擎的时间线。输出方案仍然只有官方要求的两个字段。:chatgpt-content-reference{index="8"}

下面是实际运行的单次端到端结果：

| 输入与模式 | 最终 E0 结果 | 完整墙钟 |
|---|---:|---:|
| case_002，旧三构造 | 111212 | 2.985 秒 |
| case_002，加入结构构造 | 71108 | 8.287 秒 |
| case_002，再加入一个固定窗口候选 | **66376** | **8.948 秒** |
| case_026，加入结构构造 | **28637，保留旧 cut2** | 7.693 秒 |

都使用 30 秒预算。**候选数量与实际 E0 调用次数不同，不能把这张表当成等评估次数的算法排名。**它证明的是：在这些已测用例上，收益不是靠无限离线搜索获得，选择与验证成本实际包含在内。

仍需保留工程边界：E0 子进程可以按剩余预算中断，但构造器目前是在候选之间检查时间；大图硬截止、全部 100 例与最坏耗时尚未验收。题面建议的单例 5～10 分钟目标没有被改成一个未经证明的全域承诺。:chatgpt-content-reference{index="9"}

本轮全部使用 CPU。没有 CUDA、Metal、Rust 或 C++ 的新性能成绩。当前小矩阵构造通常只占几十毫秒，**没有证据值得先为九项 max/add 单独建设 GPU 路径**；昂贵的官方展开与完整评估仍更值得优先优化。

## 九、后续最值得保留的研究方向

**第一优先级是“保护数据归属之后，选择性展开重入流水”。**当前证据说明，它可以同时避免细粒度跨核通信和过度粗化的 FIFO 损失。下一步应研究可检测的启用条件，例如重入工作量占比、响应同质性、外部依赖接口与同时就绪宽度。这样的触发器尚未验证，不能根据本轮成功例直接宣布泛化。

**第二优先级是粒度选择。**链包、小张量接口块和必要的细粒度候选互有胜负；应把“核心归属包”和“最终子图”作为两个独立层次保存，而不是寻找一套统一子图大小。

**问题 1 则继续沿 Task 释放边界研究。**覆盖关系给出精确的合法合并工具，出口和输入门控决定某次合并是否值得尝试。不能用少 Task、少搬运或少依赖边替代 Makespan 判断。

这轮尚未证明优于成熟强基线或同题头部队伍。**但已经有了一个实质进展：数学压缩不再只是论文中的解释，而是进入了构造程序，并产生了可复现的收益、明确的失败例和一个用例级质量证书。**

# 二、三项勘误分别是否造成“搜索方向偏置”

这一层比“结果文件还对不对”更重要。

### 1. F-EXEC-001 量词错误

**没有发现它让 R3 主线排除过候选。**

原因是我的 Q1 合并器没有依赖 FORM 中的 early-return 逻辑，而是自己构造完整的：

> 子图依赖边 + 每核相邻 Task 顺序边

然后重新做 DAG 检查。最终还走官方 E0。

错误量词如果被直接写入一个快速合法性代理，主要风险其实是**假阴性不足、假阳性增加**：在“一个核多 Task、另一个核为空/单 Task”的混合长度情况下，错误实现会漏检环，从而把非法候选送进后续流程。它通常不是“错杀好候选”，而是“放过坏候选”。

所以它不会解释我为什么没有探索某些好方案，但可能污染未来高速 validator 的候选池。这个风险应保留。

### 2. 24 vs 44 加核对照

这一错误**没有残留在 R3 的核心决策中**。

我在 R2 已经明确纠正：“追加空核可保留原方案，不能用异图对照证明最优值随核数增加变坏”；R3 还实际分别测试了二核、四核、五核的 `case_002`，没有因为“更多核可能有害”而停止探索。

86b 的修订也已经给出同图对照：指定分配可能更慢，但这与“可用核预算增加后的最优值”是不同命题。:chatgpt-content-reference{index="5"}

因此：

- 原 24/44 数值作为**两条并行传输共享 DDR**的小机制观察仍可保留；
- 原因果解释“核越多可能让最佳值变坏”必须删除；
- 当前串行包、3×3 响应、出口保护都不依赖这个错误。

### 3. F-TASK-006 spill 通则错误

这是三项里**唯一对未来搜索空间有实质潜在偏置**的一项。

我已经实际读取了你给的镜像反例。它证明在官方可达的 Q1 路径中，同一 L1 logical tensor 两次换入时：

- version 是一、二递增；
- 两次 `spill_out_id` 都为空；
- 两次都复用原始 COPY_IN 的 DDR backing；
- 新 incarnation 仍然是 L1；
- 官方 Q1 Makespan 为 43728。

这与冻结 `schedule_step2.py` 的分支完全吻合：只有没有 backing 时才创建 COPY_OUT 和新 DDR backing；之后复用 backing；incarnation version 每次递增；新化身位置直接取 `sp['pos']`。官方附带说明也明确：已有 backing 时不新建 COPY_OUT，原 COPY_IN 数据可以作为 backing；同一 tensor 多次换入只递增 incarnation。:chatgpt-content-reference{index="6"} :chatgpt-content-reference{index="7"}

因此，如果一个启发式曾使用类似：

> “spill 一次 ≈ 写出 size + 再读入 size”

去排序候选，它会**系统性高估已有 backing tensor 的后续 spill 成本**，尤其可能偏向过度切分大 Task。

我上一轮主构造没有实现这种费用，所以没有发现已实际错杀候选的证据；但这不等于以后可以忽略。

# 六、这轮审计后，哪些问题值得“重新深想”，但现在先不做

目前我认为真正应该留到中间层形式化审核完成后再进入第三轮的，有四个。

**第一，Q1 的存储感知 Task 粒度。**  
目前主构造几乎不显式建 spill。新勘误说明不能用一个简单的“spill 次数 × 两次 DDR”代价补进去。真正合理的状态至少要区分：是否已有 backing、L1/UB、下次使用、incarnation 次数，以及 spill 后对 FIFO/内存依赖的影响。这可能改变“什么时候应该拆大 Task”的判断。

**第二，Q1 合并判据需要从“出口保护”扩展成“释放边界保护”。**  
现有出口保护只检查 A 合并 B 后会不会推迟远端消费者；它没有完整建模 B 新引入的输入等待、DDR contention 和内部 spill。新 spill 语义使“合并后的局部成本”更加状态化。覆盖关系的合法性定理仍可保留，但**收益判据**需要重新设计。

**第三，Q2/Q3 固定归属细化在 spill-heavy 区域如何判断。**  
M4 只保证 partition 分量不变。排序变化可能改变 Step1/Step2，从而改变 spill 数量、backing 复用次数、version 链；Q3 还会改变 Cache 顺序。这一块不能由“同归属＝通信相同”继续向外推。

**第四，是否存在可压缩的 backing 状态。**  
同一 logical tensor 的 backing 一旦建立后可以复用，这其实比旧错误规则更有结构：它可能允许将 spill 成本状态压成“未有 backing / 已有 backing”再加当前 incarnation 信息，而不必把每次 spill 都当独立写回。这一点可能成为后续很漂亮的低维状态，但现在还没有做证明或正式 case 实验，不应在本轮展开。

## 命题 A：理想集与拆分后的 Task-order 无环等价

4. 使用真实 COPY 收缩关系；两半非空，新子图 ID 不冲突，覆盖不重不漏。

**必要性。**若前半不是理想集，就存在从后半进入前半的内部依赖。它与新增的“前半先于后半”核链组成环。

**充分性。**假设新 Task 图产生了环。若环经过其他 Task，将两个新 Task 都映回父 Task，删掉由前半到后半压成的自步，就得到父完整 Task 图中的非空闭合有向走法，与父图无环矛盾。若环仅在两半之间，就必须有后半到前半的边，与理想集条件矛盾。

### 外部连接不需要额外限制成某种形状

不需要要求“所有外部输入只能进入前半”，也不需要要求“所有外部输出只能由后半产生”。**两半都可以有外部输入、外部消费者。**合法父增广图已经排除了从父 Task 出去、经其他 Task 再绕回父 Task 的路径。

但两个边界不能省：

**第一，父计划仅商图无环还不够。**父图原先若已被核链补成环，以上证明无从开始。

**第二，COPY 收缩不能漏。**例如实际存在“后端操作 → Tensor → COPY → Tensor → 前端操作”，忽略中间 COPY 会误以为两端无依赖，从而错误地允许反向拆分。

**这个命题只保证 Task-order 结构合法。它不保证新局部图的内存、Step2、Step3、FIFO 执行成功，更不保证收益。**提交后依然要重新展开和评价。

这意味着：**候选生成不必绑定某条 Step1 前缀，任意内部理想集都可以作为结构合法的前半。**

# 三、B：输入释放阈值可以近线性构造最大理想集，但不能只保留最大集合

## 1. 标签应当传播“外部门控”，不要加计算时长

设父计划中本核前一个 Task 为 \(H\)，可能不存在；父 Task 旧启动时刻为 \(s_T\)。先定义本核入口底线和每个计算操作的直接外部门控：

\[
b_T=
\begin{cases}
f_H+100,&H\text{存在},\\
0,&\text{否则},
\end{cases}
\qquad
r_v=
\max\!\left(
\{b_T\}\cup
\{f_U+1000:U\text{是 }v\text{的外部异核前驱 Task}\}
\right).
\tag{I2}
\]

实际代码中，等待数值要从固定配置读取。较早同核前驱已被本核前项结束底线覆盖；这与官方 `task_release_time` 的取最大值逻辑一致。

然后沿内部拓扑序传播：

\[
\ell_v=
\max\!\left(
\{r_v\}\cup
\{\ell_u:u\in\operatorname{pred}_{D[V]}(v)\}
\right).
\tag{I3}
\]

**这里不要加操作周期。**它不是该操作的最早实际开始时间，而是：“要把这个操作及其内部先决工作放进前半，至少需要等待哪些外部 Task 完成”。

同理，原 DDR 输入的标签可以是零，但这**不表示数据已经搬入 L1/UB**；COPY 服务时间仍未计入。

对任意非空理想集，有：

\[
g_{\mathrm{frozen}}(P)
=\max_{v\in P}r_v
=\max_{v\in P}\ell_v,
\qquad
I_\tau=\{v:\ell_v\le\tau\}.
\tag{I4}
\]

## 命题 B1：阈值子水平集是该门控下唯一的最大理想集

标签沿依赖不下降，所以 \(I_\tau\) 向下闭合。

反过来，任何冻结入口门控不超过该阈值的理想集，都包含成员的全部内部祖先；其成员标签均不超过阈值，因此一定被 \(I_\tau\) 包含。

由此得到两个实用结论。

**候选数量有证明上限。**若传播后有 \(d\) 个不同标签，那么最多只有 \(d-1\) 个不同的非空真最大理想集。标签只取外部释放值及本核底线的最大值，不产生新的时间值；所以上限也受不同外部释放值数量约束。

**阈值描述可以近线性生成。**拓扑传播后按标签分桶即可，不必对每个候选重新扫描全部祖先。

不过，**输出所有完整计划并不近线性**：如果每个阈值都复制整个成员映射，仍可能出现二次开销。应该保存“阈值＋增量成员桶”，只物化选中的少量候选。

## 2. 最大理想集不能代表同阈值内的所有好方案

最大理想集回答的是：

> 门控允许提前执行的工作，最多包括哪些？

它没有回答：

> 把这些工作全部提前，是否值得付出新增 COPY、额外 Task 等待和内部重排的代价？

一个很短的早就绪分支，可能与晚就绪分支共用一份很大的输入。把这个短分支也拉到前半，会让输入读两次；把它留在后半，可能更好。

本轮的官方小例确实出现了：

- 最大早理想集比不拆更慢；
- 同阈值内的部分理想集明显更快；
- 这个部分理想集还不是父 Step1 的任何真前缀。

因此，**同一阈值只保留最大集合，会有真实的覆盖损失。**

也不能仅凭“门控、计算量、字节三项相同”合并两个不同成员集合：它们的 ID、张量接口、Step1/2/3 和 FIFO 仍可能不同。安全去重应当基于相同成员和相同计划生成规则。

## 3. 零入口提前量时，保留出口闭包

对一个异核消费者 Task \(X\)，取父 Task 中**所有向它发出真实计算依赖的源端点**，记为 \(A_X\)，构造：

\[
D_X=\downarrow A_X.
\tag{I5}
\]

**这是消除“后半直接供数给 \(X\)”所需的最小理想集。**

不能只提前其中一个输出生产者，却把另一个仍供给同一消费者 Task 的生产者留在后半；那样消费者仍要等后半完成。

这里也要收紧结论：移走后半到 \(X\) 的**直接依赖**，不表示 \(X\) 一定提前启动。它还可能等待自己的核链、其他前驱，或者经其他 Task 间接依赖后半。

若所有输入标签都等于旧启动时刻，可以证明没有**冻结模型中的入口提前机会**；但不能据此删除出口闭包、存储或局部流水所对应的全部拆分。

# 四、C：单生产者条件下，真实的 spill 前字节增量恰好能写成超图割

这是本轮最值得用来改进候选质量的部分。

**与此前全图参数割不同，这里不是猜一个通信权重。对于一次固定父 Task 的二分，我们能精确写出 Q1 builder 的 spill 前字节增量。**

## 1. 从原图的边界条件计费，不继承父 Task 的 backing

对原张量：

- 大小为 \(s_t\)；
- 唯一生产者为 \(p_t\)，若没有则视为不属于任何计算成员；
- \(C_t\) 是全部非 COPY 消费者；
- \(h_t\) 表示是否存在原 COPY_OUT 消费者；
- \(J_t\) 是其中属于父 Task 的消费者。

对父 Task 内的成员子集 \(S\)，官方边界 COPY 字节可以写成：

\[
B(S)=
\sum_t s_t
\left[
\mathbf1[J_t\cap S\ne\varnothing,\ p_t\notin S]
+
\mathbf1[p_t\in S]\,
\mathbf1[h_t\lor C_t=\varnothing\lor(C_t\setminus S\ne\varnothing)]
\right].
\tag{I6}
\]

这逐项对应官方的 `input_boundary` 和 `output_boundary`，不是从旧展开图估计。

一个容易弄错的点是：**模型中的输入 net 应当对应 builder 实际触达的原 tensor。**有原 COPY_IN 时，通常是其片上输出张量被新 Task 分别读取；不能未经核对，把所有对象重新按原 DDR ID 或 `logical_tid` 合并计费。

对于父 Task 内生产的张量，定义它原本是否已经需要写出，并定义超边切开指示：

\[
b_t=
\mathbf1[h_t\lor C_t=\varnothing\lor(C_t\setminus V\ne\varnothing)],
\qquad
\operatorname{cut}_e(P)=
\mathbf1[e\cap P\ne\varnothing,\ e\setminus P\ne\varnothing].
\tag{I7}
\]

则精确增量是：

\[
\begin{aligned}
\Delta B(P)
&=B(P)+B(Q)-B(V)\\
&=
\sum_{p_t\notin V}
s_t\,\operatorname{cut}_{J_t}(P)
+
\sum_{p_t\in V}
(2-b_t)s_t\,
\operatorname{cut}_{\{p_t\}\cup J_t}(P).
\end{aligned}
\tag{I8}
\]

## 2. 为什么有的边界收费一次，有的收费两次

| 张量类别 | 两半分开使用时的新增字节 | 原因 |
|---|---:|---|
| 生产者不在父 Task 的计算成员中，包括原 COPY_IN 输入 | 一份张量大小 | 原父 Task 读一次，新两半各读一次 |
| 内部产生，父 Task 原本不必写出 | 两份张量大小 | 生产半新增写出，另一半新增读入 |
| 内部产生，已有外部消费者或原 COPY_OUT | 一份张量大小 | 原本就需要写出，只增加另一半的读取 |
| 没有跨两半，包括纯最终输出 | 零 | 没有新增另一半的读取 |

**多个消费者不能逐条依赖边重复收费。**同一张量在一个目标 Task 读一次即可；情况 A 的源 Task 也不是每多一个目标就重新写一次。

证明就是逐张量计算两半相加与父 Task 的差。其他 Task 的成员集合没有改变，其边界布尔条件与字节数不变，因此式（I8）也是全计划 `partition_added_copy_bytes` 的增量。

但这只保证**字节不变**。生成 ID、其他 Task 的编译顺序、spill 和全局执行时刻仍可能改变；不能借此假定增量影响只限两个新 Task。

## 3. 这个集合函数可以做精确最小割

式（I8）是非负加权的 *all-or-nothing* 超边割之和，因此是次模函数。

每条超边用两个辅助点表示：所有成员连向第一个辅助点，第二个辅助点连向所有成员，容量取足够大；两辅助点之间的容量取该超边权重。成员分处两侧时，恰好支付一次权重。

本轮只针对这个装置核对了一手文献：Veldt、Benson、Kleinberg，*Hypergraph Cuts with General Splitting Functions*，SIAM Review 64(3)，2022，DOI **10.1137/20M1321048**；实际读取了开放稿 §4.1 的 Lawler expansion。**装置来自文献，式（I8）的 Q1 权重来自本题源码推导。**:chatgpt-content-reference{index="6"}

选一个理想上界 \(U\)，以及必须放前半的理想子集 \(D\)，求：

\[
\min_{\substack{P\text{为理想集}\\D\subseteq P\subseteq U}}
\left\{
\Delta B(P)-\lambda\sum_{v\in P}w_v
\right\},
\qquad \lambda\ge0,\quad w_v>0.
\tag{I9}
\]

实现时：

**依赖闭包**用反向无限容量边实现；**计算工作奖励**用源点容量实现；**强制／禁止成员**用端点无限容量实现；再接上超边装置。

一次最小割就精确求解这个标量子问题。

入口模式下，上界取某个非空真最大释放理想集。出口模式下，强制集合取出口闭包；再选一个必须留给后半的节点，禁止它及其后继进入前半，以保持二分非空。

空解应当丢弃；出口最小闭包本身也应直接保留，不能强迫所有候选经过价格筛选。

### 这是精确子问题，不是精确时间模型

计算奖励应当是**可加的工作特征**。可以另报 M/V 工作量，但不能把两类工作之和称为可重叠的真实墙钟时间。

同样，以下对象不在式（I9）里：

**动态 DDR、100-cycle 新 Task 切换、Step1 重排、spill、backing 重建、内存复用依赖及 FIFO。**

所以它不能用来硬剪枝，更不能充当 Makespan 下界。

# 五、参数扫描能压缩多少，以及哪些候选仍必须保留

固定上界、强制集合及正工作权重，随着价格增加，最优前半集合会嵌套增长。

证明可用两次最优性分别与交集、并集比较：

\[
\begin{aligned}
0
&\le
\Delta B(P_1)+\Delta B(P_2)
-\Delta B(P_1\cap P_2)-\Delta B(P_1\cup P_2)\\
&\le
(\lambda_1-\lambda_2)
\sum_{v\in P_1\setminus P_2}w_v,
\qquad \lambda_1<\lambda_2.
\end{aligned}
\tag{I10}
\]

正权重迫使前一个集合包含于后一个。

因此，在每个价格采用固定的包含极小最小割后，**一条固定参数路径最多有“成员数加一”种不同集合**。这是证明上限。

但有三个不能混淆的地方：

**有限几个价格不一定找全断点。**跨不同阈值、不同出口锚点，也不是总共只有这么多候选。

**标量化找不全离散 Pareto 前沿。**例如某个链的三个前缀分别具有工作量／字节增量：

| 前缀 | 工作量 | 字节增量 |
|---|---:|---:|
| 第一段 | 1 | 2 |
| 前两段 | 2 | 6 |
| 前三段 | 3 | 8 |

中间点不被另两点支配，却没有任何价格会选中它：要胜过第一段需要较高价格，要胜过第三段又需要较低价格，两者不能同时满足。这些字节可以由大小分别为 1、3、4 的内部链张量实现。

**代理支配不是执行支配。**更少字节、更多可提前工作，仍可能因为新 FIFO 或门控而更慢。

所以建议保留三种来源的多样性，而不是把所有东西压成一个得分：

> 最大释放理想集；价格选出的部分理想集；完整出口源集合的最小闭包。另保留少量现有前缀作为基线候选。

# 六、建议落地的单一生成流程

```text
RELEASE_BOUNDARY_SPLITS(图, 父计划, 父计划实测结果, 预算):

    校验父计划完整 Task 数据依赖+核链 DAG
    校验实测结果与父图、计划、配置的身份

    按官方 COPY 收缩关系建立计算偏序
    按原 tensor 建立精确 spill 前增量 nets

    从所有 Task 的入口/出口边界选择本轮对象
    不局限于旧生成器已经选出的高压力 Task 或两个前缀

    对每个选定 Task:
        拓扑传播外部门控标签
        一次扫描各阈值的最大理想集描述、工作量和新增字节

        选少量不同阈值，保留最大理想集
        在这些阈值内用少量价格生成部分理想集
        对少量重要远端消费者生成完整出口闭包

    保留少量既有前缀候选，按成员精确去重
    写出标准 P/Q 同核相邻计划
    再次执行官方 Task-order 检查

    用固定 E1 批接口重新编译和评价
    用 E0 确认最终方案；始终保留合法父计划
    更新父计划后，重新取得时间线并计算标签
```

**不提交内部操作顺序，不继承旧 backing，不把两个新 Task 的局部时间直接相加当全局成本。**

## 预算建议

可以用八个 split 槽启动一次对照：两个既有前缀、两个最大释放理想、两个部分理想、两个出口闭包。某类为空再回填。

**这是人为试验预算，不是理论上限，也不是说当前 E1 只能承担八个候选。**实际数量应由固定批接口的实测时间、候选编译成本和最终 E0 预留共同决定。

特别是，新方法应改变**候选入口**：先从所有 Task 的释放边界发现机会，再进入预算排序；否则仍可能重复“两个被选中的 split 都没有提前量”的覆盖问题。

## 复杂度

在真实收缩图已经取得后，设选中 Task 有 \(n\) 个计算节点、\(m\) 条内部依赖、\(p\) 个张量 pin、\(d\) 个标签：

- 标签与阈值描述可近线性处理；每条 net 的阈值割代价只在其最小、最大标签之间非零，因此可用区间加减一次算完。
- 最小割网络只有原节点加每条 net 的两个辅助点，规模与依赖和 pin 数线性相关。
- 总成本是预处理加有限次最大流，再加候选计划物化和 E1/E0。

附带参考实现采用整数 Edmonds–Karp，仅用于小 Task 和验证；它**不是生产性能版**。详细复杂度与接口在备忘中。COPY 收缩若扩张依赖，扩张后的边数必须计入；完整计划输出也有全图映射复制成本，不能藏在“近线性”里。

# 七、本轮三个有判别力的小验证

全部使用冻结配置、未修改的官方字节。没有运行正式 100 图，没有调用当前 E1/E2，没有训练。

## 1. 结构条件、边界字节和最小割目标

在固定种子的 48 张、每张 2–6 个计算节点的小图上：

| 检查 | 本轮结果 |
|---|---|
| 直接边界谓词相减 vs 式（I8） | 1060 个子集，零差异 |
| 理想条件 vs 官方计划／核链校验 | 964 个非空真二分；473 个理想拆分接受，491 个非理想拒绝 |
| 最大阈值理想与区间字节扫描 | 57 项一致 |
| 最小割 vs 穷举可行理想的标量目标 | 480 项一致，并检查参数嵌套 |

**964 次是计划 validator 调用，不是 964 次完整 E0 性能实验。**有限枚举也不替代上面的证明。

另用官方 E0 检查了一个 96-byte 内部张量、两个本地消费者、120-byte 共享输入的字节例：

| 内部张量原本是否已有外部消费者 | 只将生产者放前半 | 再将一个本地消费者放前半 |
|---|---:|---:|
| 否 | 新增 192 bytes | 新增 312 bytes |
| 是 | 新增 96 bytes | 新增 216 bytes |

正好区分“新增写＋读”“已有写、只新增读”以及“共享输入重复读取”。

## 2. 所有 Step1 真前缀都失败，非前缀部分理想成功

在固定合成图中，父 Task 的真实 Step1 计算顺序为：

**短早分支 b → 等远端输入的短分支 c → 3000-cycle 早分支 a。**

b 与 c 共用 262144-byte 输入；a 独立。冻结标签分别为 b、a 的零，以及 c 的 4002。

| 方案 | 前半成员 | Makespan | spill 前新增 COPY 字节 |
|---|---|---:|---:|
| 不拆父计划 | — | 11376 | 0 |
| 第一个 Step1 前缀 | b | 11847 | 262144 |
| 第二个 Step1 前缀 | b、c | 11477 | 0 |
| 最大早理想集 | a、b | 11847 | 262144 |
| 最小割选出的部分理想集 | **a** | **8377** | **0** |

这几项全部无 spill，原图、原 ID、核心归属保持不变。

**它说明：仅增加这条 Step1 顺序的前缀采样数量，仍然找不到这个好方案。**最大阈值集合也不能代表该阈值内的最佳取舍。

冻结标签的局限同样在这里暴露：父计划远端源结束为 3002，拆分后变为 3004；标签中的门控是 4002，实际后半启动是 4004。两新 Task 的实际执行时长合计还由原来的 7374 增到 7377。

因此，这不是固定工期反事实，也不是减少总执行时长的证明。

**负结果也保留了。**最先构造的另一输入布局中，a 恰好是 Step1 第一个前缀，部分理想只打平父计划，均为 8377；最大理想则退化到 8849。随后才构造上述非前缀变体。两个图都归档，不声称盲测，也不把重编号作为参赛动作。

## 3. 输入提前量全为零，出口闭包仍然有价值

另一个合成图中，父 Task 有两份独立工作：a 为 100 cycles，b 为 5000 cycles；异核长任务只需要 a 的输出。两者入口标签均为零。

把完整出口闭包 a 放前半、b 放后半：

| 方案 | Makespan |
|---|---:|
| 父计划 | 11005 |
| 出口闭包拆分 | **6104** |

五项搬运统计相同，spill 为零。远端任务原来在 6003 启动，拆分后在 1102 启动。

这个例子直接否定“入口提前量为零就禁止所有拆分”，但不证明零入口图上拆分通常有效。

## 八、接入时最重要的判断

**我建议试这条路线，但不建议把参数最小割作为唯一候选入口。**

真正有依据的改进是：

**用偏序闭包摆脱固定 Step1 前缀；用释放标签定位可以提前的成员；用准确的边界字节区分同阈值内的取舍；用完整出口闭包覆盖零入口提前量的情况。**

最小割只是其中一个低成本地产生部分理想集的子程序。它的优点在这次问题里有明确落点：**准确求解某次拆分的字节—工作标量子问题**，而不是维护此前没有收益的全图参数割路线。

在正式开发池中，首轮应该以相同 E1 次数和墙钟预算比较现有前缀生成器与新生成器，评价前冻结成员集合和参数。重点观察是否真正增加了有价值的**非前缀覆盖**。若只是重复原候选或增加构造费用，就暂缓默认接入；若价格筛选遗漏 E0 好方案，保留失败，降低它的筛选权重，而不是将未支持点宣布为无价值。
