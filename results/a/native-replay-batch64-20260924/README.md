# 64 个不同候选：准备成本能否摊薄

图 003、同一固定划分、4 核、64 个不同核归属/顺序候选（seed 360924..360987）。只运行一次串行批量实验，属于公开开发图；不能代表多图封存集、正式搜索算法或全部输入域。

所有 64 个计划逐个运行冻结 E0、新 E1 与原生方案。E0/E1 完整对象的类型和值全部一致；原生合并投影模式的全部操作/Task 起止时刻，以及额外 audit 模式的每次 DDR 投影记录，全部与 E0 一致。原生未消费 E0 输出或答案缓存；核对发生在计时之外。完整 E0 输出按每 16 个候选一份 JSONL gzip 流式保存，避免保留全部 trace。

| 收费口径 | 当前 E1 | 原生准备对象 + 评分 | 比值 |
| --- | ---: | ---: | ---: |
| 一次初始化/准备 + 64 次调用的累计墙钟 | 37.3302 s | 1.10888 s | 33.66× |

原生收费包括新实例、官方局部编译/校验、数组打包和 64 次候选校验、状态分配、FFI 与事件重放；第一次动态库加载包含在首次评分内。基线使用新 E1 的 16 MiB 默认缓存，首个候选编译、后续命中。两边均从已解析图与计划开始，不含 Python 解释器启动、进程池、文件 IO、IPC 或完整搜索流程；原生是内部评分接口，省略完整官方 JSON 组装。结果是实测各计时区间加总，不是独立一次不带核查的连续搜索墙钟。额外 E0 全池 truth、比较与 audit 重放用于验证，未冒充搜索必须支付的工作。

最优候选编号 16，E0 Makespan 750,898。将该候选**同一笔实测 E0 确认耗时 2.30307 s 同时加给两条路径**，得到成本核算比值 11.616×；这是从已测成本算出的确认预算示例，不是另跑正式算法的加速成绩。所有候选分数一致，所以这一池的相同排序规则选择结果一致；不据一个池宣称 95% 独立池命中率通过。

静态数值数组载荷为 1,271,343 bytes（约 1.21 MiB），不能当作 RSS。整个核查进程同时持有 E0、E1、准备对象和当前完整结果，峰值 RSS 390.31 MiB；这不表示独立原生 worker 的峰值、硬内存上限或内存降低倍数。独立进程的完整内存、并行吞吐与长跑是交接后的必验项。

输入/源码/二进制哈希、配置、初始化与逐候选原始时刻在 `run.json`、`rows.json`、`summary.json`。实际运行的原型源码快照保存在相邻 `native-replay-probe-20260924-v2/as-run-source.zip`；生成计划与完整 E0 输出均在本目录。未修改官方原件或依赖。
