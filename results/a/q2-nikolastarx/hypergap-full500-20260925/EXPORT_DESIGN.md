# Compact-summary board export: bounded design handoff

Status: **design only; no feed exporter, scoring, or benchmark result exists here**. The fresh 500-cell run is not authorized by this document. This note uses the frozen `hypergap_full500.py` at runner `16c7f2e0e7611d700b44ca7d3b79e5b39ec00632`, solver `c66559a6f8a31ef7b4720e1f7c3c28d61f8dff3f`, its `hypergap_full500_v1` manifest, and the current `docs/benchmarks/SUBMISSION_PROTOCOL.md` / `board-feed.schema.json`.

The old `scripts/q2_gap_stream_export.py` cannot be invoked on this run. It fixes solver identity to 923b, assumes a sequential accepted prefix in manifest order, reads full process and online-ledger objects from each summary row, and emits the old adaptive-gap method/provenance. Hypergap runs up to four workers and appends rows in **completion order**. Its compact row has process path/wall/RSS, ledger SHA, selected-plan SHA, result SHA/metrics, calls, and status; the complete originals are per-cell `cell.json`, `plan.json`, `online/solver.json`, `result.json`, and `solver-process/process.json` / `e0-process/process.json`. Treating `summary.rows[:N]` as graph coordinates 001… would silently mislabel results.

Minimum independent adapter contract:

1. Read the exact summary and new manifest bytes once. Check SHA, frozen solver/runner/budget, then load the pinned old 500-row baseline manifest by `baseline_manifest.path+sha256`. Build maps by `(case, cores)` and reject duplicate or unknown coordinates. Select only rows with `status=accepted`; preserve all stopped/in-flight rows in the batch audit, never fill them with a historical score. Sort **selected** rows by manifest coordinate only for deterministic archive order. A subset feed is a subset, not a full500 result. Whole500 requires `status=completed`, `accepted_cells=500`, 500 unique accepted coordinates, and empty `in_flight`.
2. For every selected cell, verify `cell.json` matches the compact summary row after removing only the two transient in-flight flags; require both process receipts `status=ok`, no surviving PIDs, and the full ledger `status=ok`, no request in flight, all attempts native/ok/problem 2, call counts and fixed E2 source identity. Check `cell.solver_ledger_sha256` against raw ledger bytes; `cell.plan_sha256` against raw plan; `cell.official.result_sha256` against raw independent E0 result. Match result `makespan`, all movement fields, cross-task traffic, scene B and core count. Do not use the compact `baseline.makespan` as the speedup denominator.
3. Archive immutable plan/result/run and full ledger/process receipts under the new hypergap result area. Gzip JSON if needed, hash stored bytes, keep raw JSON at most 64 MiB and stored blobs at most 64 MiB. The run artifact should include the exact compact row, `cell.json`, receipt references, and the summary snapshot SHA. Never edit the scoring-run files. Generate one board-submission-v1 record per *actual* accepted cell with `solver_commit=c665…`, `solver.source=src/q2_nikolastarx/adaptive_hypergap_guarded.py`, runner source/commit `16c7…/src/q2_nikolastarx/hypergap_full500.py`, fixed manifest limits and worker count, measured outer solver wall from `solver-process/process.json`, separate E0 wall from `e0-process/process.json`, online E2 count from ledger, final evaluator E0/2794…, and plan identity equal to the archived plan blob SHA. Record the actual hypergap method and selected child strategy only when the ledger supports it; do not call a mix of baseline/candidate choices a merged or offline-best plan.
4. Reuse the pinned 60af official **single-core A** reference from the old baseline feed for `baseline`, with graph/config/official identity and result blob hash checked. Never use the 923b P2 Makespan as `B`. Complete feed artifacts must be in one future archive commit; run `src/benchmark_board/protocol.py <feed> --submission` locally and require every emitted accepted cell to be eligible before any submission. Send no feed until that full path is implemented and tested with synthetic cells and at least one authentic frozen run receipt.

The two schemas differ in a way a field rename cannot solve: ordered full-row `summary.rows` versus completion-ordered compact rows plus separate originals, and old 923b adaptive-gap source versus new c665 hypergap source. A general adapter should factor out only the board record/artifact helpers from the old exporter, then implement a new `collect_validated_cells` boundary. Patching old module constants or fabricating a sequential summary would risk a plausible but misidentified board feed.
