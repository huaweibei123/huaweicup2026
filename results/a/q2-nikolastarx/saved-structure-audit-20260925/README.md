The script reads `official-cases.zip` one graph at a time, constructs an in-memory DAG index only, then discards graph/plan/result objects. It did not run a solver, proposer, E0, E1 or E2. It checked the existing report against 100 raw graph byte streams, compressed/decoded plan and result bytes, and frozen graph/plan/result identities in `cell.json`, `run.json` and `online-ledger.json`: 1,300 comparisons passed. The published `identity-readback.json` retains the report hash and check count; local execution paths remain only in the non-published output receipt.

The chain definition matches the saved gap constructor: a maximal original eligible path whose internal links have one predecessor and one successor after excluded COPY nodes are contracted. All 100 saved plans keep every such chain on one core. This is an observed restriction of this frozen archive, not proof that splitting a chain helps. There are 16 single-component graphs, 45 plans with at least one component spread across cores, and 55 plans with zero cross-core physical tensor. Strategy labels from online ledgers: 58 `adaptive_budget`, 31 `hypergap_retime`, 11 `join_gap_candidate`.

The bound is `max_pipe ceil(total original eligible cycles / 5)`, ignoring graph precedence, copies, input sharing, contention, memory and output writes. The residual `M − peak original Pipe work` is also descriptive; it cannot identify a specific waiting cause. In 005/069/071, the long residual and modest original Pipe load imbalance make chain splitting alone a weak explanation. Prepared COPY and FIFO evidence is needed before attributing the residual. In 044, 11 independent components occupy only two cores despite tiny individual chains. Its saved ledger says the route selected `active_core_shared_wave` with 930400 B of shared external input and a two-core model choice. Five-core compute balance is therefore only a hypothetical benchmark: using more cores could duplicate input service and worsen official M. This read-only comparison does not establish that 044 should activate five cores.

Next falsification should stay mechanism-specific. For 005/069/071, inspect saved official per-core timelines and cross-core transfers for COPY exposure and idle intervals, and test whether any *different* original-DAG partition can reduce that exposure without increasing traffic or violating capacity. For 044, compare the frozen two-core plan with the route's saved input-service prediction and independent-component work; a capacity- and input-aware alternative is the relevant candidate, not chain splitting by itself. Any new scoring requires a separately frozen algorithm and budget. These saved-structure rows are not a new full-algorithm benchmark.
