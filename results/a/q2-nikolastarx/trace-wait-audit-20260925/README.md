# Two recorded P2 wait traces (069/K5, 071/K5)

This is a read-only audit of two archived independent E0 results. The source is the published `results/a/q2-nikolastarx/hypergap-full500-audit-20260925/completed-summary.json` (SHA-256 `083c3f5b603cb61dd8b132718b6437b35c7706ff3aa165bdcdd490617547a2f2`). `audit.json` records exact equality of each archived `run.json` accepted row to its published row, and SHA-256 of each decompressed E0 result matching that row's `official.result_sha256`. The result makespan, movement breakdown, and cross-task traffic were checked against the row. `run.json`, compressed result, and frozen official P2 source hashes are also recorded. No evaluator, graph constructor, or solver was called.

The official P2 scheduler (`data/raw/a/official/code/multicore_cut_evaluate_problem_2.py`, `external_release`, `queue_if_ready`, `advance_pipe`, and `transfer_timeline`) processes each pipe in sequence. For a target cross-core `COPY_IN`, release is recorded as source `COPY_OUT` completion plus fixed delay. If its preceding same-pipe operation ended before release, the interval from that end to release is an observed pipe idle interval during which this target cannot run. Other local dependencies might also block it. `release == start` is consistent with release binding at that instant, but does not prove it was the unique cause.

Every positive pre-release interval ended exactly at its target's observed start in these two records. The largest 069 interval is 2467 cycles on core 4, whose recorded end is 8531, well before M=11962. The largest 071 interval is 2210 cycles on core 3, ending at 6659 before M=9465. Therefore neither largest interval can simply be called an M contribution. On the actual finishing cores, late examples are 069 core 1 target COPY_IN 1000001529: prior PIPE_MTE2 end 9850, release/start 10808 (958 cycles), and 071 core 0 target COPY_IN 1000001387: prior end 6602, release/start 8017 (1415 cycles). The `terminal_core_latest_events` field retains these records even when they are outside the largest twelve overall. Final operations are COPY_OUT 1000001809 on 069 core 1 (11936–11962) and COPY_OUT 1000001403 on 071 core 0 (9439–9465). The result omits full local operation-dependency edges and ready times, so criticality remains unknown: it cannot establish a complete critical chain from either wait to the final COPY_OUT, nor an exact avoidable M reduction.

Small next construction experiment: give late cross-core edges feeding the current predicted finishing core a co-location preference when placing packets, while retaining capacity/pipe validity and the existing independent E0 comparison. The two traces justify a targeted hypothesis, not a quality claim. Do not treat summed idle cycles as Makespan savings or reuse old COPY durations as counterfactual edge weights.

The audit used one Python process (0.05 s wall, 30 MiB maximum RSS). To reproduce, run `python3 scripts/q2_trace_wait_audit.py` from this worktree. The script reads only the two named archive cells and the published completed summary.
